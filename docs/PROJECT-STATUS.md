## 1. 这个项目是什么

**veditor** —— 一款可嵌入 AI 客户端的**极简视频剪辑器**（纯前端、无后端、无框架）。

### 产品目标

用户在 AI 客户端里生成视频、或把视频拖进客户端上下文后，**默认用这个剪辑器打开**。
界面极简四区：顶栏 / 左素材栏 / 中预览 / 右属性栏 / 底部多轨时间线。
**AI 默认完全隐形**——没有聊天侧边栏、没有常驻浮窗、没有 AI 按钮墙，
仅在用户按 `Cmd/Ctrl+K` 唤起一个底部命令栏，`Esc` 即消失。

### 用户对 AI 的核心表述（原话）

> "AI 在剪辑中扮演着辅助作用的功能，可以是个好老师基于建议帮助，也可以是个好助手协助完成任务，
> AI 几乎什么都可以做，但只要求在需要 AI 时候，AI 才会出现。"

### 技术定案（已拍板，不再讨论）

- 纯前端 + WebCodecs（**不引入播放器库、不引入 timeline 库**）
- esbuild 自写构建（**不引入 Vite/Webpack**）
- IndexedDB 持久化（无后端）
- 导出：**MP4/H.264（默认）、GIF、WAV、PNG 序列（透明通道，ZIP）四选一**
  （`ExportFormat = 'mp4' | 'gif' | 'wav' | 'png'`）。
  **WebM 只支持导入，不提供导出**（PRD Q9）
- AI：宿主注入模型（零配置）+ 云 LLM 可选，按语气自动判定建议/执行模式
- 项目参数：**跟随首个素材**（自动改写，不弹窗）
- AI 破坏性操作：**直接执行 + 可撤销 toast**，不做二次确认

## 3. 项目全史（重要节点、决策与教训）

### 3.1 2026-10-18 · 立项与地基

**产出**：PRD（64 条需求，P0 32 / P1 19 / P2 13）+ 时基规格 + 技术预检 + T01–T04。

#### 需求对齐（3 轮 11 个决策点）

形态定为「可嵌入 Web 面板（React + TS）」，预留 `?src=` / `postMessage` / Web Component 三种接入。
存储为时间线 JSON → IndexedDB，素材只存 FileHandle 引用。

**用户明确补充的产品哲学**："AI 只在该出现的时候出现" → AI 隐形化，无侧边栏/浮窗。

#### 技术预检实测结论（重要）

- **WebCodecs 与 File System Access 强制要求 secure context**：`about:blank` / `file://` 下 API 全不存在
- 解码支持：H.264 / HEVC / VP9 / AV1；编码支持：H.264 / VP8 / VP9 / AAC / Opus
- **`alpha:'keep'` 对 vp8/vp09.* 全部 false** → 透明视频无法用 WebCodecs 产出，降级 PNG 序列
- **esbuild 0.28.2 完全可用**（推翻了用户级记忆中"沙箱拦 esbuild"的旧结论）

#### webm 三个实测陷阱

1. **ffprobe 对 VP9 关键帧判定完全不可信**：报 120 个关键帧，Cues 解析真实值只有 4（VP9 alt-ref 被误判）
2. **MediaRecorder 产物是「无 Duration + 无 Cues」**：必须扫全 Cluster 才能建索引
3. **`durationFrames: null` 是合法值**（不是缺失），类型必须写 `number | null`

#### 两个团队冲突的裁决记录

- **R-015 改 fps 后片段排布**：架构师主张 ripple 右推，PM 否决 → **采纳 PM**（"用户的间隙是意图，不能替他做剪辑决定"）
- **webm 是否承诺帧精确**：架构师主张降级，PM 主张必须支持 → **采纳 PM**，新增 T19，但设止损点（超 3 天不过验收则不支持 webm，不允许"能导入但 seek 不准"的中间态）

#### ⚠️ 时基 bug 始末（本项目最重要的一课）

规格原签名 `(projectFrame, clip, asset)` 拿不到项目帧率，实现者只能用 `Clip.durationFrames` 反推比例。

- **后果**：51702 个校验点里 6993 错（**13.5%**），偏差双向
- **用户可见**：60fps 素材进 30fps 工程，正确"隔帧取 0,2,4,6…"变成"逐帧取 0,1,3,5…"
- **为何测试没抓到**：`spec:T1–T10` 全是整除组合，对反推实现完全免疫，30/30 全绿
- **修复**：签名加 `projectMilliFps` + 补 D1–D5 非整除用例 + **性质对拍**（用 BigInt 独立实现 spec 公式，不复用被测代码），64206 帧全过

> **通用教训**：规格里的每个数学公式，都必须有一组"反例用例"证明它不能被等价替换；
> 任何生死线断言，必须有一个不共享代码的独立验证路径。

`src/media/demuxWebm.ts`（~700 行）：vint 解析、未知 size 处理、TrackNumber 分流、三种 lacing。

**修掉 4 个真 bug**（每个都会让 webm 完全不可用）：
1. **fpsMilli 单位小 1000 倍**（`1e9/ns` 是帧/秒，毫帧率要 `1e12/ns`）
2. **VP9 的 description 必须 null**（传 CodecPrivate 会让 configure 静默失败 → 黑屏）
3. **previewSource 的 mp4-only 门禁**（T13 时代写的，导致 webm 进不了池）

**契约变更**：T05 ③、T12 ⑤ 的"webm 应被拒绝"断言作废，改为"probe 成功但 openMp4 仍拒绝"。

#### 真实素材排查（1080p / 旋转 / 4K / 无音频 / VFR / 长素材）

用 ffmpeg 造边界素材，发现**5 个隐蔽缺陷**（173 单测 + 19 E2E 全绿时依然存在）：

1. **1080p 预览全黑**（根因：`storeFrame` 的 LRU 淘汰会 close 帧，而 `pending.resolve` 交付的正是原帧）
   → 修：输出回调里先 `clone()` 再入缓存
2. **竖拍视频横躺**（`tkhd` 变换矩阵从未被解析）
   → 修：`parseTkhdRotation()` + 交换显示宽高 + CPU 旋转
3. **`exact = layers.length === 0 || missing === 0` 错误**（全部层失败反而判"精确"，不再重试）
4. **`void renderPreviewFrame(...)` 吞掉所有异常**（黑屏无任何提示）
5. **`allocationSize()` 默认按 RGBA 计**（1080p 算 7.9MB vs 实际 3.1MB，预算瞬间吃满）

#### 多素材组合 + 跨分辨率转场

**发现核心工作流缺陷：片尾追加片段会与前一段重叠 1 帧**。
根因：`playbackClock.maxFrame` 与 `store.syncPlayhead` **两处重复的 clamp 规则**都用 `duration - 1`。
修法：两处统一改为 `durationFrames`（时间线的"末尾点"），预览侧用最后一帧兜底。
排查方法：Node 单测证明 `seekTo(240)` 返回 240（代码正确）→ 浏览器钩子问 transport 也 240 →
但 `store.playheadFrame()` 是 239 → 锁定第二处 clamp。**"两处相同规则"的 bug，光看一处代码永远找不全。**

**跨分辨率转场确认正确**（9 项全绿）：窗口内真 2 层混合，导出 PSNR 9.7/8.2dB（证明非硬切）。

#### panel 卸载泄漏 + src 属性修复

**✅ 修复**：`<veditor-panel src="...">` 的 src 属性**从未被读过**（`connectedCallback` 硬编码 `NullAdapter`）。
T18 只测了 `?src=` 路径，没覆盖 custom element —— **"测试覆盖了集成方式的 A 路径，就以为 B 路径也对"的典型**。

**✅ 溢出问题当天稍后已解决**（详见 §7.3）：根因不是高度链断裂，而是 **`main.css` 通过 document 的 `<link>` 加载、
shadow DOM 样式隔离 → 整条 CSS 都没进去**。修法是 `connectedCallback` 把 document 的 stylesheet 克隆进 shadowRoot。
之前试的 container-query / ResizeObserver / 绝对定位三个方案方向都错了（本段曾记为"❌ 未解决"，该结论已作废）。

#### 补 P2 第一条：R-062 透明通道导出

`ExportFormat` 增加 `png`：RGBA PNG 序列 + ZIP（`frame_000001.png` 起连续编号 + `frames.json`）。

- 合成器新增 `alpha` 选项（WebGL 上下文 `alpha:true` + 清屏 alpha=0；2D 降级用 `clearRect`）；
- ZIP 自己写（`export/zip.ts`，store 模式 + CRC32 + UTF-8 名标志），不引压缩库；
- 上限 600 帧 / 4 亿像素——序列是内存里攒齐再打包的，不设闸会"导到 90% 才崩"。

验证：30 帧 ZIP 拆包后逐帧解 PNG，第 1 帧 alpha=0 占 909465 像素、不透明 7349、半透明 4789（文字抗锯齿）。

#### 补 P2 第十三条：R-057 多机位（P2 收官）

`ai/multicam.ts`：把 N 条视频轨当"机位"，按规则生成切换序列。**不新建片段**——语义是
"这一刻显示哪个机位"，所以在切换点把各机位轨 `splitClip` 切开，每个区间只让选中的机位
`enabled = true`、其余 `false`。渲染层本来就跳过 `enabled === false`（`collectVisibleClips`），
**一行渲染代码没改**。切分 + 开关在**同一批操作**里，所以一次撤销整批回滚。

能力边界（先说实话）：**没有说话人识别**。"跟说话人"用**每个机位的音频能量**近似
（`mixTimelineAudio` 单轨混音 → 取绝对值均值），一人一麦的访谈好用，共享房间麦会退化成"谁离麦近切谁"。
固定间隔模式轮流切，保证每个机位都出镜。

验证（E2E `verify-multicam`）：8 秒 / 2 机位 / 每 2 秒切 → 片段 2→8 段，
**逐帧扫 240 帧每帧恰好 1 个机位可见**（异常 0 帧），4 段机位序列 `b,a,b,a`，一次撤销回 2 段。

两个坑：
1. **"时间线比切换间隔短"必须报错，不能产出一堆关轨操作**。只有一段时"多机位"退化成
   "挑一个机位全程用"，用户会以为生效了。现在直接给可读错误（含实际时长与当前间隔）。
2. **"多机位每 2 秒切一次"不以动词开头**，`classifyTone` 的"拿不准算提问"会把它判成提问，
   于是命令栏什么都不做。`looksImperativeFor()` 的动作词表补 `机位` / `跟说话`。

#### 补 P2 第十二条：R-056 蒙版

`render/mask.ts`（参数求值 + 关键帧覆盖 + 方位词映射）+ 着色器 `maskAlpha`（矩形/椭圆 + smoothstep 羽化）。
验证：一句话"遮住左边"后平均亮度 127.6 → 61.4（正好一半），撤销回 127.6，`lastGlError=0`。
关键设计：关键帧挂在 **effect** 上（复用 `Effect.keyframes`），不动 clip 的关键帧管线。

#### 补 P2 第十一条：R-058 LUT

**踩了一个会白屏的坑**：`sampler3D` 没有默认精度（`sampler2D` 有 lowp），不写 `mediump` 编译失败——
而着色器编译失败会让整个编辑器白屏，不只是丢 LUT。另一个坑：在模板字符串里写反引号注释

验证：载入提亮 LUT 后平均亮度 127.6 → 146.6，`lastGlError=0`，撤销回 127.6。

#### 补 P2 第十条：R-059 字幕

#### 补 P2 第三条：R-052 代理媒体

`media/proxy.ts`（4K → 960px 长边，视频 + AAC）+ IDB `proxies` store（DB 1→2）+
`previewSource` 的双源表（预览/导出分开取）。

**踩坑（花了最久）**：切源只调 `engine.registerAsset` 会保留旧源的**帧缓存**，
切过去取第 0 帧命中旧缓存 → 预览黑屏，而且之后没有任何事件会再重绘（看起来"代理是黑的"）。
修法：`unregisterAsset`（释放会话 + 清缓存）→ `registerAsset` → **等到真的画出一帧**（`decoded === true`，
因为 `renderFrame` 会合并并发请求）。诊断过程：先确认代理文件本身没问题（ffprobe 抽帧 YAVG 126）、
再确认解码帧不黑（画布统计 128）、最后发现合成器"层数 1 / 跳过 0 / 无 GL 错误"却输出黑——
三者同时成立只可能是画的是旧缓存帧。

#### 补 P2 第二条：R-060 智能粗剪

`media/silence.ts`（20ms 窗口 RMS → dBFS）+ `core/rippleDelete.ts`（切两刀 → 删中间 → 整轨左移）
+ `ai/roughCut.ts`（混音 → 检测 → 倒序编译 → 一次 dispatch）。

**关键分工**：模型只判意图（要不要剪、多长算长），位置必须本地算——模型看不到波形。
所以命令栏在调模型**之前**就用 `parseSilenceRequest` 拦下这条指令；模型若返回 `removeSilence` 意图，
编译器给出可读错误而不是"未知意图"。

**踩坑**：`compileRemoveRange` 剪尾只改出点，会在原地留洞；粗剪必须用波纹删除（后面整体左移）。
单测里第一版期望值算错了（忘了"后段左移会把更后面的片段一起带过去"）。

### 3.5 2026-10-21 · 打通语音识别通道（R-059 的最后一公里）

R-059 原来只做了"SRT 导入/导出"，边界写着"语音识别未做，因为 `AIModelPort` 只有
`complete(prompt)`，没有音频输入"。这一轮把那条通道补上了——**客户端仍然不做 ASR**，
但链路不再是断的：

```
时间线 → 混音（48k 立体声）→ 下混单声道 → 重采样 16k → 宿主 transcribe() → 清洗 → 字幕轨
```

分工与粗剪/多机位一致：**宿主负责"听懂"，客户端负责"把音频变成它要的格式、把结果变成时间线"**。

- 端口扩展：`AIModelPort.transcribe?(request)`（可选！不实现 = 没有这个能力），
  `AIProvider.transcribe?` 同步透传。**故意不兜底成"返回空数组"**——那会让用户以为
  "识别完成了，只是没人说话"，而真相是"这台客户端没有识别能力"。
- 新增 `media/asrAudio.ts`：`downmixToMono`（取平均，不是取最大声道）、
  `resampleLinear`（48k→16k 线性插值，误差集中在高频，ASR 特征提取本来就要低通）、
  `rmsOf`（整段静音就别浪费一次宿主调用）。
- 新增 `ai/transcribe.ts`：`parseTranscribeRequest`（"自动生成字幕/帮我转写"；提问不接）、
  `segmentsToCues`（**清洗不可信输入**：时间戳倒着、乱序、重叠、空文本、负时间）、
  `transcribeTimeline`（抽音频 → 转写 → 清洗 → 一批 op）。
- 字幕落轨抽成 `subtitle/srt.ts` 的 `buildSubtitleReplaceOps`：**整段替换**（字幕是唯一的，
  重复识别不该叠两份），SRT 导入与语音识别共用这一份实现。
- 新增 timebase 原语 `secondsToMs` / `msToSeconds`（宿主回传秒、字幕内部毫秒；`sec * 1000`
  是守卫会拦的裸换算）。E6 导出清单从 12 个函数变成 14 个。

**验证**（`verify-transcribe`，10 项）：装一个假宿主，它检查自己收到的音频——
**16000Hz / 128000 采样（正好 8.00 秒）/ rms 0.088**，返回 3 条好片段 + 2 条坏片段；
客户端丢掉坏的、3 条字幕落点精确到帧（0+45 / 60+45 / 180+36）；重复识别是整段替换（仍 3 条）；
两次撤销分别回到上一次结果与清空；拔掉通道后给可读拒绝且**不产出空字幕**。

> 这条链路里最容易坏、也最难用单测覆盖的是"混音 → 下混 → 重采样"那一段（要真 WebCodecs）。
> 为此给测试钩子开了 `installTranscriber()`：它只换一个通道、不碰 doc，生产构建里不存在。

### 3.6 2026-10-21 · 落轨规则修正：多机位从"代码里有"变成"用户能用"

写完 R-057 后回头看这条 E2E，发现它当时**只能用 `setProject` 硬造一个双轨工程**——
因为界面上根本没有"把第二段素材放到第二条轨"的路：`AssetPanel.defaultTrackId()` 是
一句"视频永远 `trk_V1`、音频永远 `trk_A1`"。

这条规则带来两个问题：

1. **同轨重叠**：播放头落在已有片段上时双击素材，第二段被塞进 V1 与第一段重叠。
   渲染层会把两段都解出来画一遍（后画的盖住前面的，看起来"没反应"），
   音频混两遍（**音量翻倍**）。而且它是合法操作（点两下就到），不是极端场景。
2. **多机位不可达**：多机位要求"一条视频轨 = 一个机位"，用户却没有入口建第二条有内容的轨。
   功能做完了、命令也接了，但用户永远触发不到——这比没做更糟（文档写着支持）。

修法：把落轨规则抽到 `core/placement.ts`（纯函数，12 条单测）：

- `trackRangeFree`：区间**左闭右开**判定（前一段结束点 = 后一段起点不算重叠，这是正常剪辑）；
- `pickTrackForInsert`：先看首选轨（V1/A1，保持"第一段素材落 V1"的既有预期），
  再按屏幕顺序找**未锁定、未隐藏、区间空闲**的同类型轨；都没有返回 `null`；
- `nextTrackFor`：新建轨（`V{n}`/`A{n}`，`order` = 同类轨数量）——与「＋ 轨道」按钮共用，
  避免"点按钮建 V3、双击素材建 V2"这种重名。

`addToTimeline` 现在：找到空闲轨就用；没有就**新建轨 + 放片段在同一批操作里**（一个撤销步）。

**验证**：`verify-multicam` 的 ① 改成了真实路径——`?src=` 已经占用 V1，
再双击素材卡 → 第二段落到 **V2**，两条机位轨都能出画（非黑像素 921161），
随后多机位切换 8 段、逐帧单机位可见、一次撤销回滚。回归 t12 / multiclip / project-file /
a-ui / c-ui / t16 / touch-a11y 全绿（t12 断言"第一段落 V1"仍然成立，因为那时 V1 是空的）。

> **教训**：功能的"可达性"也要验。R-057 的单测和 E2E 都是绿的，但 E2E 用 `setProject`
> 绕过了真正的入口——**测试绕过的路径，就是用户走不通的路径**。

### 3.7 2026-10-21 · 轨道从"只增不减"到可删

上一节把落轨规则修好之后，一个新的缺口立刻暴露出来：**轨道只能加，不能删**。
界面有「＋ 轨道」，双击素材在全部占用时还会**自动新建轨**，但没有任何删除入口——
用户误点几下就攒出一堆空轨，永远清不掉。这属于"改了 A 之后 B 才暴露"的那类问题。

补齐方式：

- `core/placement.ts` 加 `trackRemoveBlockReason(doc, trackId)`：不能删时返回**可读原因**，两条规则——
  1. **至少要留一条视频轨**（删光之后字幕落轨 `buildSubtitleReplaceOps` 直接失败，
     用户会以为编辑器坏了）；
  2. **锁定的轨不能删**（锁定就是"别动这条轨"，删除是最彻底的"动"）。
  有内容的轨**允许删**——撤销栈能整体回退，拦着反而逼用户一个个删片段。文案里带片段数。
- 轨道头右上角加 `×`（`data-v="remove-<trackId>"`），不可删时 `aria-disabled` + `title` 说明原因，
  点击给错误条提示而不是静默失败。
- 删除走 `removeTrack`（本来就与 `addTrack` 互为精确逆操作），所以**一次撤销能把轨道和片段都带回来**。

**验证**（`verify-tracks`，11 项）：＋轨道建出 V3 → 双击素材落 V3（V1 占用）→
全占用时自动新建 V4 → 删 V4（轨与片段一起消失，轨 4 条/片段 3 段）→ 一次撤销回来（轨 5 条/片段 4 段）→
删到只剩 V1 时再删被拒绝（`aria-disabled=true` + 错误条"至少要保留一条视频轨"）。

### 3.8 2026-10-21 · 隐藏/锁定开关，以及"锁了要真的锁住"

上一节补完删除入口后，`locked` / `hidden` 这两个字段的状态就很尴尬：

- **`hidden` 是"有规则没入口"**：渲染、音频、转场、导出、多机位全都认这个字段，
  但界面上没有任何开关——用户既藏不了轨，也解不开工程文件里藏着的轨。
- **`locked` 是"有入口没规则"（更糟）**：它只影响"自动落轨"和"能否删轨"，
  **锁上之后照样能拖、能裁、能删片段**——那这个锁就是假的。而当时连解锁入口都没有。

这一轮两件事一起做：

1. **三个轨道开关统一成一个操作** `setTrackFlag { flag: 'muted'|'hidden'|'locked' }`。
   原来只有 `setTrackMuted`，再加两个平行操作会让 apply/inverse/文案 三处都复制三遍；
   合并之后 `store.setTrackFlag(trackId, flag, value)` 是唯一入口（`verify-a-ui` 的静音用例照旧绿）。
2. **锁定守卫放在 `applyOperation` 入口**：`clipTracksForOp(doc, op)` 列一张"操作 → 受影响轨"的表
   （`addClip` / `moveClip`（含移出与移入两条轨）/ `rippleShift` / 所有 `clipId` 类操作），
   锁了就抛 `TrackLockedError`。**轨道级操作（解锁/改名/删轨）不在此列**——否则锁上就再也解不开。
3. **拒绝要给用户看，bug 要给测试看**：`store.record` 只捕获 `TrackLockedError` 转成错误条
   （"轨道已锁定，先解锁再修改"），其它异常照旧抛。第一版是 catch 全部，结果
   `clip-ops` 的"非法倍速应当抛"用例立刻变红——**它替我抓住了"统一 catch 会掩盖真 bug"这件事**。

**验证**（`verify-tracks` 扩到 15 项）：隐藏唯一视频轨 → 预览非黑像素 921161 → **0**，再点回来 → 921161；
锁定后按 Delete → 片段还在 + 错误条"轨道已锁定"；解锁后同样的 Delete → 片段 0 段。
单测侧 `core` 加 4 条：三个开关各自独立且逆操作精确还原、锁定轨上 move/trim/remove/addClip 都抛、
锁定仍可解锁与改名。

> 一条经验：**字段被渲染层认 ≠ 用户能用；字段有入口 ≠ 规则生效**。
> `hidden` 缺前半句的入口，`locked` 缺后半句的守卫，两个都得补上才算"支持"。

### 3.9 2026-10-21 · 把"全量 E2E"固化成一条命令，顺手修两个边界

前面几轮抓到的 4 个真问题，全都来自"人工排查"。其中"全量 E2E"只跑过一次——
靠临时脚本，跑完就删了。**没固化 = 下次还得靠运气**，所以这一轮先补这张网：

**`npm run e2e`**（`scripts/e2e-all.mjs`）：42 个 `verify-*.mjs` 串行跑完，汇总 + 失败清单 + 非零退出码。
两个设计取舍写在脚本头里：

- **串行**：每个脚本自己起 dev server + 浏览器，端口是写死的（5201–5222），并行会撞端口。
- **给子进程去掉 `CODEBUDDY_SAFE_DELETE_BULK_*`**：这个环境对"单轮批量删除"有闸（阈值 50），
  而每个脚本都 `rmSync` 自己的 `tests/.tmp/<name>`。连跑 42 个必然把配额用光，
  最后几个会死在"清理临时目录"——`verify-realworld-export` 就这样假红过一次。

第一次全量跑（42 个）：**41 通过 / 1 失败**，失败的是 `verify-transition-mixed` ⑤
"三个时刻画面都非黑（920792 / **0** / 291405）"。单跑立刻通过——**不是回归，是负载下的解码竞态**。

连着跑了 **5 次**才稳定，过程本身很说明问题——**每次红的都是不同脚本**：

| 第几次 | 结果 | 红的是谁 | 真因 |
|---|---|---|---|
| 1 | 41/42 | `transition-mixed` | `inspectAt` 等 2.4s 就拍快照，负载下还没解出那一帧 |
| 2 | 41/42 | `m4-ai` | 命令栏按钮 `disabled` 竞态（点在被吞掉） |
| 3 | 41/42 | `realworld` | 固定 `sleep(2000)` 就拍快照 → 拍到全黑 |
| 4 | 40/42 | `roughcut` + `realworld` | 前者同上；后者 `decodeFailures=1`（见下） |
| 5 | **42/42** | — | 9.2 分钟 |

修的都是"等条件"而不是"等时间"，以及两个**指标本身的假警报**：

- **`decodeTest()` 会取消正在跑的渲染**：`verify-realworld` 的 `inspect()` 里，
  `decodeTest ×3`（诊断用）排在快照**前面**，它 bump epoch 取消了引擎的渲染，
  之后拍的快照就是空的（层数 0 / 全黑）。改成"先拍快照与统计、再跑诊断"。
  这个坑之前一直存在，只是被"负载下渲染本来就慢"掩盖了。
- **`decodeFailures` 把"epoch 取消"算成解码失败**：连按两次 seek 就会发生，是正常行为
  （新请求会重画）。算进去之后这个指标在负载下永远非 0，诊断变"狼来了"。
  现在 `decoderPool` 导出 `EPOCH_CANCEL_MESSAGE`，引擎只统计**真的**解码失败。

**结论**：`npm run e2e` 现在是一条可信的命令（42/42，9.2 分钟）。每个脚本的完整日志落在
`tests/.tmp/e2e-logs/`，失败时直接看它，不用重跑。

顺手修的两个边界（都是"用户能输入越界值、错误还静默"）：

**① 转场时长没有和片段长度关联**。`commitTransition` 只夹 0.1–2 秒，10 帧的片段照样能设 2 秒转场。
而转场窗口是**以接缝为中心**的（前半在外、后半在内），窗口比片段还长时，片段结束时进度还不到 1
→ **画面永远半透明**（像蒙了层灰，很难归因）。进出都挂转场时更明显。
修法：`core/types.maxTransitionFrames(clip)` = `floor(durationFrames / 2)`，三处共用——
属性栏夹（用户拖不出来）、`projectInput` 导入时夹（宿主可能送旧版工程）、
`planTransitions` 渲染时再夹一次（兜底，防越界数据）。
为什么是一半而不是"不超过片段"：进出各占一半时，中间**必留一整段完全不透明**的画面。

**② SRT 的重叠 cue 会变成同轨重叠的文本片段**。SRT 允许两条时间轴交叠（双语字幕、
工具生成），但落到时间线上就是两个文本片段叠着画——谁都看不清。
修法：把重叠消解抽成 `srt.resolveCueOverlaps(cues)`（排序 → 前一条尾巴收到后一条起点 →
不足 40ms 丢弃），**SRT 导入与语音识别共用这一份**（原先 ASR 侧有一份独立实现）。
`buildSubtitleReplaceOps` 现在回报 `truncated`，顶栏文案会写"3 条重叠已截短"——
有损操作必须说出来，否则用户看到"条数比文件里少"却不知道为什么。

### 3.11 2026-10-21 · 音频"一直沙哑"：逐块重采样是元凶

用户补了第 2 条的细节（素材来自微信、无代理徽标、音频一直沙哑但播放器正常）。**没有再猜**——
直接把那个文件复制出来用 ffprobe 探测：

```
video: hevc 720×1280 29fps 894kbps
audio: aac LC **44100Hz 单声道** 48kbps
```

由此定位两件事：

**① "画质被压缩" 主要是文件本身。** 微信把发出的视频重编码成 720p、不到 1Mbps 的 HEVC；
原片若是手机直录（1080p+、几 Mbps），差的是这个文件。我们的预览也不额外降采样
（画布后备缓冲跟随容器，实测 1401px > 素材 720px）。

**② "一直沙哑" 是真 bug：预览音频逐块重采样。**

预览音频按块（约 160ms）解码排期。旧代码对**每一块**单独调用 sinc 重采样（44.1k → 48k）。
我们的 sinc 核有 16 个抽头，需要块边界**之外**的样本才能算对边缘；逐块调用时边缘被 clamp，
每块两端各约 32 个样本是错的 —— 一秒切十来个块 = 每秒二十来处 1.3ms 的失真，听感就是持续沙哑。

修法：**不再自己逐块重采样**，把**源采样率**的 `AudioBuffer` 直接交给 WebAudio
（它在播放时做整段高质量重采样，没有边界问题）。`applyDenoise` / `applyClipGain` 的采样率
参数同步改成源采样率。

顺带修的两个相关缺陷：

- **声道数以 AudioSpecificConfig 为准**：微信在 `stsd` 的 `channelcount` 里写 2，真实是单声道。
  位序 `[objectType 5][freqIndex 4][channels 4]`，`freqIndex === 15` 时布局不同、直接放弃猜测。
- **命令栏"打开即重置"的时序 bug**：重置写在 `useEffect` 里，effect 在首帧之后才跑，
  按完 Ctrl+K 立刻打字会被清空（表现为"字自己没了 / 运行按钮一直是灰的"，负载下必现）。
  改成**条件挂载**（每次打开都是新实例），初始 state 天然干净。

**验证**：新增素材 `aac-44k-mono.mp4`（44.1kHz 单声道）；`verify-audio-playback` 每条素材多一条
断言——**排期 PCM 的字节/秒 ≈ 源采样率 × 声道 × 4**（有人把逐块重采样加回来会立刻红）。
全量 E2E **43/43（9.9 分钟）**。

> **教训**：这个 bug 从 T10 就在，一直没被发现，因为**我们的测试素材几乎全是 48kHz**
> （唯一一个 44.1k 的 `sample-720p.mp4` 也只在"有没有声音"这一层被验过）。
> **采样率这种"恰好绕开就没事"的维度，必须有专门的素材覆盖。**

**够细致**：右键菜单从 5 项扩到 7 项，重点是用户点名的音频三件事：

| 菜单项 | 行为 |
|---|---|
| 分离音频 | 原片段 `role='video'`（只出画）+ 音频轨新建 `role='audio'`（只出声） |
| 导出这段的音频… | 只把**这一段**混成 WAV：区间=片段区间 + `onlyClipId` 只让它参与 |

**实现上的三个决定**：

1. **`ExportRequest.onlyClipId` 而不是"另写一条单片段导出"**——`mixTimelineAudio` 已经是
   "整段、确定性、零空洞"的混音器，加一个筛选参数就够；另写一条必然与主路径漂移。
2. **抽 `media/importPipeline.probeMediaFile()`**——"探测 → 资产 → 注册预览源 → 缩略图"
   原来只写在素材栏。多一个导入入口时抄一遍，就必然出现"素材卡片有缩略图、上轨后黑屏"
   （漏 `registerPreviewSource`）这种只有一处能用的 bug。
3. **抽 `core/placement.buildPlaceAssetOps()`**——素材栏双击上轨与新入口共用同一套落轨规则与
   时长换算，否则会出现"双击落 A1、右键配音频落 A2"。

**顺手抓到的三个真 bug**（都是"看起来能用、实际走不通"）：

- **空白处右键的分支永远走不到**：旧代码 `if (hit.clipId === null) { setMenu(null); return; }`
  在判空时就返回了，于是下面"`clip === undefined` → 粘贴到此处"那段是死代码 ——
  **"粘贴到此处"从上线起就没生效过**。判空必须放在"取到片段之后"。
- **导出混音漏了 `role` 过滤**：`audioMix.audibleClips` 没有跳过 `role === 'video'`，

### 3.14 2026-10-22 · "先了解常规剪辑软件"：行为基线 + 旋转/定格/倒放/吸附开关

用户给了一个比具体功能更重要的反馈：

> 删除音频等这些功能不是一次性，不是你使用过就无法继续使用的了……
> 我希望你能够更智能一点，更能理解一下常规剪辑软件是怎么样的。
> 我觉得你现在首要目标是先去了解常规剪辑软件是什么样的，再来协助我制作。

**所以先做了一件事：写 `docs/nle-baseline.md`** —— 把剪映 / CapCut / PR / FCP 在
"音画分离、定格、倒放、逐帧、吸附、旋转"六件事上的行为逐条列出来，标清楚
**我们照做还是有意偏离、为什么**。这份文档现在是加剪辑功能的入口：
先查基线，再决定怎么做，而不是想到哪加到哪。

#### ① 修掉"一次性功能"（用户实测的那条）

`分离音频` 原来判 `clip.role === 'video'` 就拒绝，于是"分离 → 删掉声音 → 再也不能分离"。
判据改成**派生**的：看时间线上还有没有同源音频片段（同 `assetId` + 源区间相交）。

- 有 → 拒绝，且文案告诉用户"声音已经在 A1 上，删掉它就能重新分离"；
- 没有（被删了）→ 允许，从源素材再取一次（`role` 已经是 video 时不重复写，免得撤销栈多一步空状态）。

这条原则写进了基线文档第 0 节：**状态派生，不记历史**。
每加一个"用过了"的判断，都要问"这看的是当前状态还是历史动作"。

#### ② 旋转 90° + 水平/垂直翻转

`Clip.transform` 加 `rotation / flipX / flipY`；渲染走 `render/frameTransform.ts` 的纯函数
（GL 用 mat2，2D 降级用 canvas 变换，两条路径逐字对应）。只做 90° 步进：
任意角度会引入画面外黑边，而"自动放大裁掉多少"是个产品决策，容易做得很糟。

#### ③ 定格帧（3 秒）+ 倒放（只倒画面）

两者都**不改渲染，只改映射**——`mapProjectFrameToAssetFrame` 里加两个分支：

- `freeze` → 恒返回 `inFrame`（于是定格片段就是一个普通片段：能拖能裁能删能撤销）；
- `reversed` → 返回 `outFrame - 1 - offset`（**不反向解码**：逐帧 seek 会长到不可用，
  而"读到的帧放到相反的时间点"效果完全一样）。

定格要 ripple：切一刀 + 插入 3 秒 + **所有轨**上插入点之后的片段整体后移
（只推本轨会让配乐/字幕/第二机位相对错位，音画全散）。

#### ④ 吸附：本来就有，补了开关

`snapFrame`（R-022）一直在跑，但用户看不见也关不掉。补：工具栏「吸附 开/关」+
`N` 快捷键（跟剪映；PR 是 `S`）+ 按住 `Alt` 临时关。状态放 ephemeral
（不进工程、不进撤销栈）——切换吸附不该让 `Ctrl+Z` 有事可做。

**顺手发现**：只读 `store.getEphemeral()` 时按钮标签不刷新，因为 `notify()` 后
`useDerived` 的派生对象在 doc 没变时是同一个引用，React 判定"快照没变"就不重渲染。
用 `useVersion()` 订阅"任何状态变化"才真的会刷新。

#### 这一轮的三个真 bug（都是"看着对、其实错"）

1. **着色器里旋转乘在了缩放之前** —— 单位正方形转 90° 还是那个正方形（几何上恒等），
   于是画面**完全没转**，只是宽高互换生效了。必须"先按 u_size 缩放，再旋转"。
   这个 bug 用肉眼几乎看不出来（时间线片段变宽了、属性栏也显示 90°），
   是 E2E 量"左右是否留黑 + 顶部是否仍有画面"才抓到的。
2. **右属性栏只有 110px 宽**，四个按钮排两列时溢出被 `overflow:auto` 裁掉一半 ——
   `elementFromPoint` 直接命中属性栏本身，表现就是"按钮看得见、点不到"。改单列全宽。
3. **工程文件序列化漏了 `role`**（本轮补 `freeze/reversed` 时发现）：`createClip` 只在
   参数里带了才写字段，`normalizeClip` 又没读 `role` —— 存盘再打开，分离音频的片段
   会变回"画面和声音都有"，音量翻倍。这类 bug 从界面上完全看不出来，只有存盘再开才炸。

**验证**：`frame-transform` 19 单测 / `freeze` 11 单测 / `detach-audio` 12 单测；
新 E2E `verify-transform`（14 项，量黑边）、`verify-freeze-reverse`（12 项，量"真的冻住了"）。
倒放的像素级断言放在单测里——因为测试素材几乎是纯色，E2E 里比对帧亮度等于比较两个相等的数，
**看着绿其实什么都没证明**，这条已写在测试注释里。

### 3.15 2026-10-22 · 顾问方案落地第一步：把素材拖进时间轴（P0-1）

顾问方案（`docs/product-plan.md`）盘出来的**最大缺口**是这一条：
`TimelineView` 里**没有 `onDrop`** —— 素材只能双击上轨（永远落 V1 的播放头位置），
而目标里写的是"全拖拽式交互"。这是唯一一个"用户每天用几十次、之前完全做不到"的入口。

**做了什么**

| 环节 | 落点 |
|---|---|
| 拖起 | 素材卡 `draggable` + `ui/dnd.ts` 的自定义 MIME `application/x-veditor-asset` |
| 接收 | `TimelineView.onDragOver / onDragLeave / onDrop` |
| 落点预览 | `EphemeralState.dropGhost` + `timelinePainter.drawDropGhost`（蓝块=可落、红块=不可落） |
| 落点解析 | `core/placement.buildPlaceAssetOps(doc, asset, frame, { trackId })` |
| 吸附 | 复用 R-022 的 `snapFrame`（8px 阈值），`Alt` 临时关、`N` 整体关 |

**四个必须讲清的设计决定**

1. **为什么用自定义 MIME 而不是 `text/plain`**：素材栏已经有一个"整窗 drop = 导入文件"的监听，
   内部拖拽若塞 `text/plain`/`Files`，拖一张卡会同时触发"导入"和"上轨"。
   分 MIME 之后两边各认各的。
2. **为什么落点预览与真正 drop 走同一个函数**：`planForDrop()` 两边都调，
   于是"目标位置被占用 → 系统换到另一条轨"时，ghost **直接画在那条轨上**——
   看到的就是落到的，不会出现"我明明拖到 V2，怎么跑到 V1 去了"。
3. **为什么校验下沉到 `core/placement`**：视频拖到音频轨必须**明确拒绝**并给可读原因，
   而不是偷偷换个轨放进去（`pickTrackForInsert` 拿到 `preferId` 后只在同类型轨里退让）。
   拒绝理由有四种：轨道类型不符 / 已锁定 / 已隐藏 / 轨道不存在。
4. **为什么 dragover 阶段要用页面内变量传素材 id**：HTML5 规定 dragover 时
   `getData()` 返回空串（安全限制），而落点预览要提前知道"这段素材多长"才能画出宽度。
   `ui/dnd.ts` 用一个模块变量传递，`dragend`/`drop` 都清掉。

**顺手修掉一个老 bug**：`timelinePainter` 里算轨道行号用的是 `doc.tracks` 的**存储顺序**
（A1/V1/V2），而绘制与点击用的是 `trackDisplayOrder`（V2/V1/A1）——两者在默认工程里正好相反。
于是 V2 上片段的**拖动 ghost 会画到 A1 那一行**。E2E 之前只拖过 V1
（存储序号与显示序号恰好都是 1），所以一直没暴露。现在统一走 `trackRowIndexOfClip/Track`。

**验证**：`verify-dragdrop.mjs` 19 项，其中三条是这一轮的关键：
- **落点误差 ≤1 帧**（拖到 120 → 落在 120）；
- **预览 = 落点**（ghost 的 trackId/startFrame 与最终片段一致）；
- **预览真的画出来了**（读画布像素：可落偏蓝 480/480、不可落偏红 80/480）——
  只断言 state 的话，painter 忘了画也会一路绿，用户看到的是"拖了半天没反应"。
另有吸附（239 → 240）、关掉吸附后不贴（239）、视频拖音轨被拒且不产生片段、
拖到轨道头列不接、`dragend` 清预览。

**数字**：471 单测 / 28 脚本；E2E 47 个脚本；构建 584.7KB。

### 3.16 2026-10-22 · 用户实测两个 bug：音量"调了不管用" + 加轨后下面的轨看不见

用户报了两条（附截图）：① 素材在 V1 时"只有画面没声音"；② 音量调到 5% 还是过响。
查下来**这两条是同一个 bug**，另外还揪出一个布局问题。

#### ① 音量：显示值改了，实际值没改（根因）

`InspectorPanel` 的音量滑块原来是：

```tsx
onChange={(e) => setGain(Number(e.target.value))}   // 只改本地 state（界面数字）
onPointerUp={() => commitAudio({ gain })}            // 松手才写 doc
```

于是只要 `pointerup` 没落在滑块上（点轨道跳值、键盘调、触摸在别处抬起），
**界面显示 5%、文档里还是 100%**。表现就是"5% 也过响"；
如果某次把滑块拖到 0 而 `pointerup` 落在别处、或 `gain` 是上一拍的旧值，
文档里就会留下 `gain = 0` —— 而界面不会显示 0，
于是下一条反馈变成"这条轨只有画面没声音"（V1 那条正是这样，V2 没调过所以正常）。

**修法**：
1. `onChange` 立即提交（`commitAudio({gain}, {mergeKey})`），显示值永远等于真实值；
2. `store.dispatch` 新增 `options.mergeKey`：**连续同键操作合并成一条撤销记录**
   （窗口 1 秒，保留最早的 `inverses`、`ops` 里保留最早的 `from`），
   于是"拖一次音量 = 一个撤销步"，而不是二十个；
3. 时间线上给**静音片段**画红色「静音」/「只出画」标记 —— 这类"没声音"从此一眼可见，
   不用靠选中它去右栏猜。

#### ② 预览音量没到引擎

`setMasterVolume` 用的是 `master.gain.setTargetAtTime(...)`。斜坡挂在 `ctx.currentTime` 上，
而 **AudioContext 在用户点播放前是 suspended，这个时间不前进** —— 于是"播放前先把音量调小"
完全不生效（实测 `master.gain.value` 一直是 1）。改成直接赋值（主音量整体缩放、步进 0.05，
听不出跳变）；同时引擎重建后会把当前音量补一次（`volumeRef`），否则重绘一次就变回 100%。

#### ③ 加轨后下面的轨道被挤出视口（"拖不到 V3"）

时间线区域高度固定（`--v-timeline-h`，默认 220px），而画布高 = 标尺 + 轨数 × 56：
4 条轨就要 248px，`overflow: visible` 让画布直接溢出 —— 1280×720 下 **A1 整条在视口外**，
看不见也就拖不进去。现在画布放进 `.v-tl-scroll`（`overflow-y: auto` +
`scrollbar-gutter: stable`），轨道再多也能滚到；轨道头按钮改挂在 `.v-tl-inner` 里，
跟着画布一起滚（否则滚动后按钮和轨道会错位）。

#### ④ 花屏：没能复现，但加了一道保险

用户截图里"片段放在后面、前面播放出乱码"。用 6 种素材（720p / 1080p / HEVC / 4K /
竖屏旋转 / 10 分钟长片）逐条试，**片段之前都是纯黑**（`nonBlack = 0`），复现不出来。
仍然加了两道保险：
- `compositor.endFrame()` 在**零图层**时再清一次屏（防止某个提前 return 让 FBO 残留上一帧）；
- `pcmProbe()` 暴露 `masterGain`，以后"音量到底有没有到引擎"可以直接读。

**验证**：`undo-merge.test.mjs` 8 项（合并/撤销/重做/不同键/被隔开不合并）；
`verify-audio-controls.mjs` 10 项（音量 5% 真写进 doc、连续拖动=一步、撤销回原位、
静音标记出现/消失、预览音量到引擎、加轨后可滚动到最后一条轨）。

**数字**：479 单测 / 29 脚本；E2E 48 个脚本；构建 585.7KB。

### 3.17 2026-10-22 · 音量改成 dB 映射（线性振幅的"手感"问题）+ 峰值保护

用户给了一份很具体的规格：**对数 dB 映射、100% = 0dB、0% 静音、200% = +12dB、超 0dB 软限幅、界面显示 dB**。

#### 旧实现为什么"手感不合理"

`gain = 滑块值`（0..2 线性振幅）时：100% → 0dB，**50% → 只有 -6dB**，25% → -12dB。
也就是滑块下半程承担了 -∞~-6dB，上半程只承担 6dB —— 拖起来"前半段几乎没变化、后半段一脚踩空"；
而且 200% 只到 +6dB，拿不到"小幅放大"。

#### 现在的映射（`core/volume.ts`，纯函数 + 16 条单测）

```
0%              100%                200%
│                │                   │
-∞ dB  ←──────  0 dB  ────────→   +12 dB
   (衰减 60dB)        (增益 12dB)
```

- `0 < 位置 ≤ 1`：`dB = -60 + 60 × 位置`（每 1% 走 0.6dB）
- `1 < 位置 ≤ 2`：`dB = 12 × (位置 - 1)`（每 1% 走 0.12dB）
- `位置 = 0`：**真静音**（振幅 0，不是 -60dB 的 0.001）

上下半段斜率不同是**故意的**：人耳对衰减的容忍度远大于放大，调音台的推子也都是下半程行程大。
关键是"每段行程对应的听觉变化量一致"，所以全程手感是均匀的。

**存储仍然是线性振幅**（`clip.audio.gain`）：老工程 `gain = 0.5` 的声音一点不变（还是 -6dB），
只是滑块会显示在 90% 的位置——**声音优先，界面其次**。`projectInput` 把上限夹到 +12dB 对应的 3.98，
防止手改工程文件塞一个 100 进去变成 +40dB 爆音。

#### 峰值保护（软限幅）

`softLimit(x)`：|x| ≤ 0.9（-0.9dB）**恒等**，超过之后用 `tanh` 渐近到 **0.999**（不是 1.0，
给 16bit PCM 留一点余量）。三个地方用同一份实现：
- 预览：`applyClipGain` 里，**只在该片段可能超过 0dB 时**逐样本走（衰减路径不付代价）；
- 导出：`mixTimelineAudio` 对最终混音再限一次（多轨叠加也可能超 0dB，先扫峰值，没超就完全不动）。

#### UI

- 属性栏音量：滑块位置 0–200%，标签**以 dB 为主**（`-∞ dB` / `0.0 dB` / `+12.0 dB`），百分比作辅助；
- 控件条预览音量：同一套曲线、同样显示 dB；
- 静音（0%）时时间线片段左端有红色「静音」标记（上一轮加的），三处信息互相印证。

**验证**：`volume.test.mjs` 16 项（三个锚点 / 全程单调 / 往返一致 / 软限幅恒等区+天花板+奇函数+单调 /
dB 文案）；`verify-audio-controls.mjs` 扩到 18 项（含"200% 播放峰值 ≤ 0.999 且削顶样本 0"）。
受影响的 `verify-c-ui` / `verify-preset` 同步改成按"位置 → 振幅"断言。

**数字**：495 单测 / 30 脚本；E2E 48 个脚本；构建 587.1KB。

### 3.18 2026-10-22 · S1 几何收敛 + S2 轨道头改造（时间轴规范落地第一批）

1. **`placement.ts` 自己声明了一份 `TrackKind = 'video' | 'audio'`**，遮蔽了 types 里的同名类型 ——

### 3.19 2026-10-22 · 预览花屏 + 轨道状态不实时（两个核心体验 bug）

用户报了两条（附截图）。查下来是**四个独立缺陷叠在一起**，其中两个互相掩盖，
所以只修一个的话另一个会让现象看起来"没修好"。

#### ① 花屏：`preserveDrawingBuffer: false` + "不绘制就不管了"

WebGL 上下文是 `preserveDrawingBuffer: false` 时，浏览器**合成过一次之后就不再保证
绘制缓冲的内容有效**。而预览是"有变化才重绘"的（暂停时不画）——
只要暂停后发生任何一次重新合成（窗口缩放、切主题、面板重排、切标签页回来），
显示的就是那块**未定义内存**：黑白噪点、横向条纹，正是截图里的样子。

修法：**`preserveDrawingBuffer: true`**。不是为了截图（截图走 FBO 读回），
而是"暂停时画面必须稳定"这个硬保证。代价是每帧多一次缓冲拷贝
（1080p 约 0.1–0.3ms，不随片段数增长）。另一条路是常驻 rAF 每帧重画，
暂停时也白烧 GPU，笔记本风扇会响——不选。

#### ② 清屏被 `clear` 参数控制，而"有没有内容"和"要不要清"是两件事

`beginFrame(frame, clear)` 的清屏是条件式的。任何一个调用方传 `false`、
或者某条路径压根没走 `beginFrame`，FBO 里就是上一帧/未初始化内容。
现在两条渲染路径（WebGL / 2D 降级）**无条件整张清**。

同时补了 `endFrame` 里最容易漏的一格：**层数组非空但每一层都被跳过**
（源失效 / 尺寸为 0）。判据是"本次跳过数 == 层数"，此时再清一次。

#### ③ 空内容没有"明确的成功语义"，把重试预算耗在重画黑屏上

`renderPreviewFrame` 只在 `exact === true` 时清零 `retryBudget`。而"空内容"
（空工程 / 播放头在空隙 / 轨道全隐藏）在 element 模式下 `exactSeek` 恒为 false，
于是**每次都判成不精确 → 重试 5 次 → 预算耗尽 → 之后所有重绘直接返回，一帧都不画**。
用户看到的就是"切回显示轨道也不刷新"。

修法：
- `FrameResult` 新增 `empty`（本帧本来就没有可见层），引擎在 `visible.length === 0` 时
  **显式走一次 beginFrame + endFrame 后返回 `empty: true`**（不做任何解码）；
- `renderPreviewFrame` 认 `empty` 为成功，不消耗预算；
- `decoded === false`（被合并进在途渲染）也不算失败；
- 新增 `repaintPreview()`：**无视预算**强制重画，供状态变更使用。

#### ④ 无效帧没有拦截，`missing` 不计数 → `exact` 假阳性

解码器吐出尺寸为 0 的帧（`VideoFrame` 被 close、`HTMLVideoElement` 未拿到 metadata）时，
合成器 `drawOne` 会跳过该层，但引擎侧的 `missing` **不增加** → `exact` 判成 true →
上层不再重试 → 预览永久停在"清过屏的黑帧"，而用户以为"这段素材是黑的"。
现在引擎侧先 `isDrawableSource()` 校验，尺寸非法按 `missing` 处理并关闭该帧。

#### ⑤ 轨道状态变更：画面不重绘、音频不掐断

两个原因叠加：
- **画面**：`store.subscribe` 确实会重绘，但被上面的重试预算卡死（③）；
- **音频**：播放中的 PCM 是**提前 1–3 秒排期**的。用户点静音时，未来的块早已在
  WebAudio 队列里，改文档对它们没有任何影响 → "点了静音，过一会儿才静音"。

修法：**每条轨一个闸门（GainNode）**，串在"片段增益 → master"之间。

```
片段 source → 片段增益（音量/包络，已烘进 PCM）→ 轨道闸门(0/1) → master → destination
```

`applyTrackGates()` 按 `isTrackAudible(doc, track)` 直接赋值 `gate.gain.value`，
下一个音频量子（约 3ms）生效，**不打断任何在途的块**。
选它而不是"`stop()` + 重新 `start()`"：后者会咔哒 + 丢几十毫秒 + 重排有解码延迟。

**为什么直接赋值而不是 `setTargetAtTime` 平滑**：`AudioParam.value` 在自动化期间读到的
**不是实时值**（实测一直是 1），于是"静音到底有没有到音频链路"在 E2E 里根本测不出来——
这正是这类 bug 反复回归的原因。硬切的代价（理论上一个样本台阶）远小于"点了没反应"。

#### ⑥ 统一入口：收敛在 `store` 订阅点

按钮、右键菜单、Agent/API 全都走 `store.setTrackFlag` / `dispatch`，最终都是同一次 `notify()`。
所以在 `store.subscribe` 里用**轨道状态指纹**判断"这次是不是轨道状态变了"：

```
变了 → audioRef.applyTrackGates()（音频立刻掐/放）
     → repaintPreview()（画面强制重绘，暂停也画）
```

收敛在订阅点，而不是在每个按钮的 `onClick` 里各写一遍——否则迟早漏一个入口。

#### ⑦ 顺手收敛的两处 solo 遗漏

`collectAudibleClips` 和 `clipsNeedingExtraDraw` 还在用 `track.muted || track.hidden`，
**漏了独奏**（solo 时其它轨应当让位）→ 表现为"点了独奏，别的轨还在响 / 转场边界外那一侧
还被画进来"。现在两处都走 `isTrackAudible` / `isTrackVisible`。

#### ⑧ 时间线画布：隐藏轨道压暗（两个视觉陷阱）

要求"空轨道、隐藏轨道绘制前先铺底色"已经满足（每帧 `clearRect` + 每行整条铺类型底色）。
额外加了"隐藏轨整行压暗"，踩到两个坑：

1. **压暗必须画在轨道头列的 `rulerBg` 之后** —— 先画会被那层浅色整块盖住，
   表现为"代码明明加了，画面一点没变"（实测 245→245）；
2. **必须用黑色蒙层，不能换底色** —— 轨道底色本身就浅（`#f5f5f5`），换成
   `trackAlt`(`#f0f0f0`) 只差 2–3 个色阶，肉眼完全看不出。10% 黑蒙层压掉约 25 个色阶。

#### 验证

`tests/verify-preview-empty.mjs`（12 项）**读可见画布像素**，不是 `previewSnapshot()`：

> `previewSnapshot()` 读的是合成器的离屏 FBO——那个缓冲**一直**是干净的。
> 用户看到的花屏发生在"上屏后的可见画布"上，所以只有 `drawImage(canvas)` 再读像素才测得到。
> 这也是这两个 bug 长期没被自动化抓到的主要原因。

覆盖：空工程 / 空隙 / 有片段（对照组）/ 暂停隐藏 / 取消隐藏 / 全隐藏 /
播放中静音（闸门 300ms 归零）/ 取消静音 / 独奏 / **dispatch 路径（Agent）** /
时间线压暗 / 性能。

单测：`track-layout.test.mjs` +6（`collectVisibleClips` / `collectAudibleClips`
在隐藏、独奏让位、空隙、静音四种情况下的"本帧有没有内容"）。

**数字**：515 单测 / 31 脚本；E2E 49 个脚本；构建 594.2KB。

### 3.20 2026-10-22 · S3：轨道高度拖拽 / 复制轨道 / 上移下移 / 拖拽排序

S3 的目标是"轨道本身可编辑"：高度、顺序、复制。**没有一条是新增界面元素**，
全是把已经能点但做不到的事接上。

#### 两个新 op（其余全是组合）

```ts
{ op: 'setTrackHeight'; trackId; from; to }              // 高度，apply 里夹 24–120
{ op: 'reorderTracks'; changes: Array<{trackId, from, to}> }  // 批量改 order
```

**为什么排序是"批量改 order"而不是"单条改 order"**：同类型轨道的 order 必须保持
`0..n-1` 连续。单条改很容易撞号（两条轨同一个 order → `trackDisplayOrder` 退化成按 id 排，
用户看到"拖了但没动"）。一次把整组重算完，顺便天然是一个撤销步。

**复制轨道不是新 op**，是 `reorderTracks` + `addTrack` + N×`addClip` 的组合（`core/trackOps`）。
这样一次 dispatch = 一个撤销步：复制一条带 20 个片段的轨，Ctrl+Z 一次全回去。

#### `core/trackOps.ts`（新）

| 函数 | 职责 |
|---|---|
| `buildDuplicateTrackOps` | 复制轨道（含片段、继承静音/隐藏/锁定/独奏/高度） |
| `buildShiftTrackOps` | 上移 / 下移（同类型组内交换） |
| `buildMoveTrackOps` | 拖拽排序（目标下标 → 整组重算 order） |
| `trackDropTarget` | 指针画布 y → 目标下标 + 指示线位置（纯函数，可单测） |
| `heightFromDrag` / `clampTrackHeight` | 高度换算与夹取 |

**复制的三个硬要求**（都在注释里）：
1. 片段 **id 全部重新生成**——同 id 会让 `findClip` 命中旧片段，复制出来的轨跟着原轨一起动；
2. 新轨插到原轨**上方**（`order = 原 + 1`，上面的整体 +1）；
3. **锁定/静音/隐藏/独奏/高度全部继承**——复制一条静音的轨，期待它还是静音的。

片段用 `structuredClone` **整份深拷贝**，只换 `id`/`trackId`。为什么不用
`createClip({...逐字段})`：`Clip` 有 15+ 个字段，而 `CreateClipParams` 只覆盖一部分，
手写映射**必然漏字段**，漏掉的那个恰好是"用户刚调过的那个效果"。

#### 排序只能在自己那一组里

视频/音频/字幕互不跨越。跨组移动会打乱"字幕在最上 → 视频居中 → 音频垫底"的层级，
而用户看不出原因。到边界时 ⋮ 菜单项**置灰并把原因写在文案里**（"上移（已经在最上面）"），
和"删除轨道"同一个套路：先解释为什么不行，比点了没反应好。

#### 高度拖拽：window 上监听 + mergeKey

- 热区在轨道头**下边缘 5px**（规范写 3px，实测 1080p 上压不住 3 个物理像素，
  用户会以为"高度不能调"），向下溢出 2px 压在行分隔线上，hover 变主色；
- `pointermove` 监听在 **window** 上：指针一旦移出那 5px 热区，元素上的 move 就收不到，
  拖动会"卡住"；
- 每次 move 都 dispatch，但带 `mergeKey: track-height:<id>`：撤销栈只留一步，画面跟手。

#### 拖拽排序：4px 阈值 + 只画指示线

- **移动超过 4px 才算拖**：同一位置还要响应双击改名。若 pointerdown 立刻进入拖拽，
  双击的第一下就把轨道拖起来了，改名永远触发不了（E2E ⑪ 专门钉这条）；
- 拖动中**只画指示线**（`ephemeral.trackDrag`），松手才 dispatch：
  实时改 order 会让整条时间线重排（所有片段的 y 都变），画面抖动 + 几十个撤销步；
- 指示线**贯穿整条画布**（含轨道头列）：用户是从轨道头拖起来的，只看内容区会不确定插在哪。

#### 这一轮踩到的三个坑（都是"看着对、其实错"）

1. **`from` 取在了 `drag.current = next` 之后** —— 第一步变成 `next → next`（无效 op），
   合并后最早的 from 是 70 而不是 60，表现是"撤销一步只回到中途的某个高度"（实测 60→100 撤销回 70）。
2. **排序拖拽直接把 `clientY` 传给了 `trackDropTarget`** —— 那个函数要的是**画布坐标**。
   屏幕坐标大几十上百，于是指针"永远落在最下面那行"：拖到最上面算出 `targetIndex=2`，
   松手后顺序纹丝不动。
3. **测试里给 `top` 又乘了一次 DPR 比例** —— `trackLayout` 的 `top` 已经是画布 CSS 像素，
   再乘 0.5 就落到标尺区，`targetIndex` 恒为 0。

#### 验证

- 单测 `track-ops.test.mjs` 22 项：复制（字段逐字一致 / 深拷贝 / 继承 / 重名 / order 连续）、
  上移下移（含"不跨类型"）、拖拽排序（越界夹取 / 位置没变不产生撤销步 / 落点中线判定）、
  高度（夹取 / 影响布局 / 撤销）、op 文案
- E2E `verify-track-s3.mjs` 14 项：拖下边缘改高（含撤销一步回原位、上限夹到 120）、
  ⋮ 复制（轨数 +1 / 片段一起复制 / 插在原轨上方 / 撤销一步全回退）、
  上移下移、边界置灰带原因、拖拽排序（指示线出现 → 松手提交 → 撤销）、
  双击改名仍可用、跨类型不越界

**数字**：537 单测 / 32 脚本；E2E 50 个脚本；构建 600.7KB；76 文件 0 处非法换算。

### 3.21 2026-10-22 · 素材持久化与重链（"刷新必离线 + 重新链接无效"）

用户报：刷新后素材全部离线、点「重新链接」什么都不发生、离线素材看不出区别。
查下来是**四个独立缺陷**，其中两个互相掩盖（"重链其实做了，但刷新又丢"）。

#### ① 「重新链接」按钮什么都不发生

旧实现：

```ts
const granted = await requestAssetPermission(stored.value);  // ← await
if (!granted.ok) { pushError('无法自动授权…'); input.click(); }  // ← 已脱离用户手势
```

`await` 之后浏览器的 **user activation 已经过期**，`input.click()` 被静默拦掉
（内嵌面板里 100% 被拦）。于是"点了按钮 → 弹一句无法自动授权 → 文件框不出现"，
用户只能反复点，永远修不好。

修法：**点按钮的第一件事就是打开选择器**（支持 `showOpenFilePicker` 就用它，
能拿到句柄；不支持就同步 `input.click()`）。"恢复授权"拆成**另一个动作**
（顶部离线条的「恢复访问」），它才是 `requestPermission` 该待的地方。

#### ② 重链"成功"了，刷新又离线

旧重链走 `importAssetFile(file, assetId)`，它把素材写成
`sourceMode: 'memory'` + `handleRef: null` —— 下次刷新必然又离线。
用户看到的是"重链根本没用"。

修法：统一到 `media/relink.ts` 的 `relinkAssetFromFile`：
探测新文件 → **写回同一个 assetId** → 清解码缓存 → 写缩略图与句柄 → 立刻重绘。
有句柄就落 `fs` 模式，刷新不用再选。

#### ③ 刷新后必然离线（最根本的一条）

`restoreSession` 原来只把 `asset.status` 标成 `ok`，但 **`previewSource` 的源表是内存态**，
刷新后是空的 —— 引擎没有字节可解，状态是好的、画面是黑的。

修法：`restoreSession` 新增 `restorableFiles`（权限 granted 的素材直接 `handle.getFile()`），
App 拿到后逐个 `probeMediaFile(file, null, assetId)` 重新探测并注册。
**不 await**（10 个素材要 1–2 秒，阻塞会让页面白屏），每完成一个自己重绘一帧。

顺带修了一处：`getFile()` 失败（文件被移走/改名）时降级成 `offline` 而不是标 `ok` ——
"权限还在、文件没了"是最常见的离线场景（用户整理过素材文件夹）。

#### ④ 注销没生效：素材"离线"了画面还在动

`engine.unregisterAsset` 用的是 `pool.release`（**只关会话、保留源**），
下一次 `ensureFrame` 会重新建会话并成功解码 —— 等于没注销。

修法：`unregisterAsset` 改成"**先同步 `invalidate`（删源 + 清帧缓存）、再异步关会话**"。
同步那一步是必须的：调用方紧接着就会重绘，异步删除赶不上那一帧。

#### 新增的模块

| 文件 | 职责 |
|---|---|
| `media/relink.ts` | `relinkAssetFromFile`（单素材）/ `relinkFromFiles`（批量）/ `scoreCandidate`（打分） |
| `media/fileHash.ts` | 前 1MB 指纹（SHA-256，无 `crypto.subtle` 时降级 FNV-1a） |
| `ui/App` 的 `OfflineBanner` | 顶部离线条：N 个离线 + 重新链接 / 批量重链 / 恢复访问 |
| `ui/App` 的 `PreviewOfflineHint` | 预览区「素材已离线」（只在当前帧确实有离线片段时显示） |

#### 匹配打分（自动重链的判据）

```
指纹一致                      → 100  （唯一可以无条件链的情况）
名字 + 大小 + 时长 三项全对    → 100  （达到 AUTO_LINK_SCORE=95）
只有名字相同                  → 40   （重名文件太常见，绝不自动链）
名字不同但大小+时长一致        → 60   （用户改过名，需人工确认）
```

**为什么名字只给 40**：用户重命名文件（`IMG_0001.mp4` → `片头.mp4`）是重链的
主要场景之一，名字权重太高会让这种情况永远匹配不上。

#### 视觉标识（四处，互相印证）

- **时间线片段**：40% 灰蒙层 + 左上角红底「离线」角标（与"静音"徽标错开纵向位置）；
- **素材卡**：左上角「离线」角标 + 原有的"重新链接"按钮；
- **预览区**：画面下方「素材已离线」+ 重新链接按钮；
- **顶部离线条**：琥珀色（不是红色——红色在这套配色里表示"危险操作"，
  而离线是**可修复的状态**）。

#### 这一轮踩到的三个坑

1. **`engine.unregisterAsset` 内部是 `void pool.unregister(...)`（异步）**，
   和紧跟着的同步 `register` 打架，把刚注册的源删掉 → "重链成功但画面永远黑"。
   最终改成：池的 `register` 自己负责清旧会话与帧缓存（覆盖语义）。
2. **`pool.release` 不删源**（只关会话）→ 注销无效，见 ④。
3. **时间线角标的像素判据不能用"偏红像素数"**：角标那一小块区域里本来就有素材画面的红
   （实测离线 187、恢复后仍有 144），必须用**相对差值**判"角标消失了"。
4. **`void asyncFn()` 启动的 promise 会穿插进调用方的后续 await**：
   给 `pool.register` 加"覆盖注册先 `void release()`"之后，`release` 的异步段
   把**导出混音刚缓存的音频样本**清空了 —— 症状是 **MP4 导出没有音轨**
   （WAV 却正常，因为 WAV 不走视频封装）和**智能粗剪找不到停顿**。
   即使把 `cache.removeAsset` 提到 `release` 的同步段也没用：真正的问题是
   "同步注册 + 异步清理"这个组合本身。最终改成**纯同步的 `invalidate`**
   （同步摘会话引用、异步只关资源），注册路径上不启动任何带副作用的 promise。

### 3.22 2026-10-22 · 自动恢复优先（刷新后用户零操作）

上一轮把"手动重链"修好了，但**默认路径仍然是手动**：每次刷新都要点一次「恢复访问」。
这一轮把它翻过来 —— **自动恢复优先，手动只是兜底**。

#### 四层策略（从上到下，能自动就绝不问人）

```
第 0 层  宿主（Electron）按绝对路径直读        → 不查权限、不问用户
第 1 层  句柄还在、权限 granted               → getFile 直接重建
第 2 层  句柄失效/文件被移走                  → 静默扫描"授权过的目录"匹配
第 3 层  以上全失败                          → 才显示离线条（手动入口）
```

#### 第 0 层：宿主路径（Electron 100% 自动）

新增 `media/hostFiles.ts`：宿主只要在 bridge 上实现一个方法，

```ts
window.veditorHost.readFileByPath = async (path) => new Blob([await fs.readFile(path)]);
```

恢复流程就会**优先走它**——文件就在磁盘上，既不会"权限过期"，也不需要用户点任何东西。
没有 bridge 时 `hasHostFileAccess()` 返回 false，整条路径被跳过，**不需要业务代码里到处判断环境**。

#### 第 1 层：并行恢复（10 个素材 < 1 秒）

`restoreSession` 原来是串行 `for` + `await`：每个素材要串"读句柄 → 查权限 → 取文件"，
10 个素材是 30 次 await 排队（实测 1.5–3 秒）。三步之间没有数据依赖，改成整体 `Promise.all`。

App 侧的探测也限并发 4（不是无限并发）：IDB/权限查询是轻量的，但 `probeMediaFile`
要 demux 读 moov，同时解 10 个 4K 会打满 CPU。

#### 第 2 层：静默扫描（这里有一个必须说清的浏览器限制）

**浏览器拿不到"某个文件的父目录"**（安全限制），所以"文件改名后扫同级目录"
只有**用户显式授权过那个目录**时才做得到——也就是他点过「批量重链…」选过文件夹。

于是：
- 批量重链选目录时，**把目录句柄存进 IDB**（新 store `directories`，DB v3）；
- 刷新后对仍然离线的素材，静默扫描这些目录（递归 1 层，最多 400 个候选）；
- 匹配规则**完全复用** `relinkFromFiles`（指纹 100 / 三项全对 100 / ≥95 才自动链）；
- 扫出来的候选**带句柄**，所以自动重链后素材落 `fs` 模式，下次刷新不用再扫。

没有授权目录时这一层直接跳过，`scanned = 0`——**不假装扫过**。

#### 导入即请求持久权限

Chrome 的 `showOpenFilePicker` 返回的句柄只在本次会话有效，刷新后 `queryPermission`
变回 `prompt`。只有在**用户手势内**调 `requestPermission` 并选「始终允许」才持久。

所以在 `openPicker` 里、拿到句柄后**立刻**请求一次（只对第一个句柄：同一 origin 的
同一权限浏览器只弹一次，循环请求 10 次也是白搭）。

#### 闸门：恢复期间不弹离线条

`restoreSession` 会先把取不到文件的素材标成 `offline`，紧接着第二层再把它们链回来。
如果这时就弹离线条，用户会看到"1 个素材离线"闪一下又消失——比不提示更让人不安。

所以加了 `autoRestoreDone` 状态：恢复期间只显示一条**灰底、无按钮**的
「正在自动恢复 N 个素材…」（刻意做得不像警告），全部尝试结束后才变成琥珀色离线条。

#### 降级

| 环境 | 行为 |
|---|---|
| Electron（有 bridge） | 第 0 层直读，100% 自动 |
| Chromium 已授权 | 第 1 层，自动 |
| Chromium 未授权但授权过目录 | 第 2 层扫描，自动 |
| 内嵌面板 / 无 FS Access | 全部跳过，直接进第 3 层（离线条 + 批量重选） |

#### 验证

- 单测 `auto-restore.test.mjs` 12 项：扫描（只收媒体扩展名 / 递归一层不过界 /
  候选带句柄 / 单文件失败不中断 / 无 `values()` 不抛 / 候选上限 400）、
  编排边界（没有离线素材不扫目录 / 没有授权目录时 `scanned=0` 且全部进"需手动" /
  权限不是 granted 记 `deniedDirectories` 不扫）、宿主路径识别（POSIX / Windows / 相对路径不认）
- E2E `verify-relink.mjs` 扩到 21 项：新增"恢复期间只显示正在恢复、无手动按钮"
  与"恢复结束才显示离线条"

**数字**：565 单测 / 34 脚本；E2E 51 个脚本；构建 618.8KB；80 文件 0 处非法换算。

### 3.23 2026-10-22 · 本地草稿素材缓存池（终极兜底）

前四层恢复都依赖**外部条件**：宿主路径、文件句柄权限、授权目录。
任何一条断了（用户挪文件、清站点数据、换浏览器、内嵌面板不给权限），素材就救不回来。
缓存池把**字节**复制进软件自己的存储 —— 从此不再依赖源文件是否还在原地。

#### 恢复优先级（缓存排第一）

```
1. 本地草稿缓存池（OPFS / 宿主 drafts/assets）   ← 新增，唯一不受外部条件影响
2. Electron 宿主绝对路径直读
3. 持久化句柄权限恢复
4. 授权目录静默扫描匹配
5. 标记离线，显示手动重链入口
```

#### 两个后端

| 环境 | 后端 | 说明 |
|---|---|---|
| Electron 外壳 | `veditorHost.copyAssetToCache / readCacheFile / listCache / clearCache` | 主进程 `fs.copyFile`，2GB 也不用进渲染进程 |
| 浏览器 | **OPFS**（`navigator.storage.getDirectory()`） | 持久、刷新不丢、**不需要任何授权** |
| 都没有 | 无 | 自动跳过，行为与旧版本完全一致 |

**为什么是 OPFS 而不是 IndexedDB**：OPFS 的 `createWritable()` 是**流式**写，
2GB 素材不会把内存打满；IndexedDB 存 2GB Blob 会让标签页直接崩。
而且 OPFS 同样"源私有"、同样持久，还省掉了 IDB 的事务开销。

#### 命名即去重

缓存文件名 = 内容指纹（前 1MB SHA-256）+ 原扩展名：

```
sha256-8fb1bae1…493.mp4
```

同一份素材导入三次 → 三次算出同一个指纹 → 落到同一个文件 → **天然去重**。
冒号被替换成短横：Windows 文件名不允许 `:`，而 Electron 侧这就是真实文件系统。

#### 无阻塞 + 无缝切换

导入流程是「探测 → 注册预览源 → 用户已经能拖上轨」，**之后**才把拷贝任务丢进队列：

- 并发 **2**（拷 2GB 时磁盘 IO 已接近打满，再高会让预览解码卡顿）；
- 完成后把 `cacheKey` 写回素材（`store.updateAsset`），**不动原句柄记录** ——
  缓存只是"多一条保命路径"，原句柄没坏就该留着，下次还能走更快的句柄层；
- 失败**不报错**（缓存是锦上添花，不该打断用户）。

#### `relinkAssetFromFile` 的 `handle` 语义要区分三态

这一条是缓存接入时最容易错的地方：

| 值 | 含义 | 用在哪 |
|---|---|---|
| `undefined` | **不改变**原句柄记录 | 从缓存恢复（缓存不该顶掉还能用的句柄） |
| `null` | 显式清掉句柄 | 用户手动选文件（`<input>` 拿不到句柄） |
| 句柄 | 写入新句柄 + 落 IDB | `showOpenFilePicker` 路径 |

同时 `cacheKey` / `contentHash` **必须从旧 asset 继承** —— 它们不在 `probeMediaFile`
的探测结果里，不显式带上就会"重链一次，缓存记录丢了"。

#### 缓存面板（顶栏「缓存」）

- 显示后端类型（OPFS / 应用数据目录）、文件数、占用大小；
- **自动缓存开关**（关掉后新导入不再缓存，已有缓存保留）；
- 「清理未使用素材」：按当前工程的 `cacheKey` 集合判断；
- 「清空全部缓存」：二次确认。

**为什么必须有这个面板**：缓存会悄悄占磁盘（一份 2GB 素材就是 2GB）。
没有管理入口的自动缓存，迟早变成"用户发现 C 盘满了却不知道为什么"——
那比"刷新丢素材"更糟。

#### 这一轮踩到的四个坑

1. **`assets()` 测试钩子做了字段裁剪** —— 加 `cacheKey` 之后 E2E 读不到，
   一度以为"缓存写了但没记到素材上"（实际是钩子没暴露）。加字段时**要同步改钩子**。
2. **`evaluate` 的字符串里不能用顶层 `await`** —— 报的是
   `SyntaxError: missing ) after argument list`，很容易误判成别的语法问题。
   要用 promise 链（`.then((v) => JSON.stringify(v))`）。
3. **`localStorage` 写不进去时开关会失效**：隐私模式/受限 iframe 里
   `setItem` 抛错，只靠它就会出现"用户关了开关，下一个导入还是写了缓存"。
   加了一份**内存兜底**（本次会话一定生效）。
4. **性能断言又被机器负载骗了一次**：同一份代码空闲时 0.1ms、跑满测试时 14ms。
   阈值放到 25ms 只防"数量级回退"，并在注释里写清"不假装能测出 10% 的差异"。

#### 验证

- 单测 `draft-cache.test.mjs` 11 项：键规范化（冒号/扩展名/无扩展名）、
  去重（同指纹三次只存一份）、并发上限（6 个任务峰值 ≤2）、
  开关（关闭不写、无后端不抛）、统计与清理（`unusedEntries` / `inUseCacheNames`）
- E2E `verify-draft-cache.mjs` 12 项，核心是 ④：**把素材标离线 + 清掉预览源
  （模拟"源文件被删 + 刷新"），只靠缓存池就能把画面救回来**，且片段属性逐字未变；
  另有面板统计、开关、缓存键在恢复后不丢

### 3.24 2026-10-22 · S4：片段四态（默认 / 悬停 / 选中 / 锁定）

按 `docs/timeline-spec.md` §3.1 落地。这一轮最有价值的不是"加了三种状态"，
而是**发现两处"实现了但没接上"**。

#### ① 悬停态是死代码

`drawClip` 里早就有 `isHovered` 分支（边框变色），但 `ephemeral.hoverClipId`
**从来没有被写过** —— `onPointerMove` 只在拖动时干活，不拖就直接 return。
所以那段代码从上线起就没执行过。

修：`onPointerMove` 里没在拖时做 `hitTest` → `store.setHoverClipId(hit.clipId)`。
`setHoverClipId` **值没变就不 notify**（指针在同一片段内移动时每帧都会调它，
无条件 notify 会让每个 mousemove 都重绘整条时间线）。

#### ② 锁定按钮"看起来有效、实际没拦住"

`timelineController.pointerDown` 里**完全没有 `locked` 判断** —— 轨道锁了，
片段照样能拖、能裁。锁定只改了轨道头图标的颜色。

修：`pointerDown` 在 `select` 之后拦一道：

```
锁定轨 → 允许选中（用户要能看属性/去解锁），拒绝拖动与裁剪，并给一句可读提示
```

顺序很重要：先选中再拦。如果连选中都拦掉，用户点一下完全没反应，会以为界面坏了。

#### 四态的判定与视觉

优先级 **锁定 > 选中 > 悬停 > 默认**。为什么锁定压过选中：锁定是"这段不能动"，
选中是"我正看着它"。锁定的片段被选中时如果还画主色描边，用户会以为可以拖 ——
而拖动确实会被拒绝，那种"看着能拖、拖了没反应"的落差比"一看就不能拖"糟得多。

| 态 | 视觉 |
|---|---|
| 默认 | 1px 细边（`--v-border`） |
| 悬停 | 叠 10% 白（"亮度提升"）+ 半透明把手（55%） |
| 选中 | 2px 主色描边 + 实色左右把手 + 四角 3px 锚点 |
| 锁定 | 30% 黑蒙层 + 1.5px 灰描边 + 右上角「锁」角标（不画把手） |

**悬停为什么不用 `ctx.filter = 'brightness(1.1)'`**：那个滤镜会走一条离屏合成路径，
100 片段重绘时是实打实的开销（T15 的 0.1ms 指标是这条红线）。叠一层半透明白
在视觉上几乎等价，而 `fillRect` 是纯光栅操作。实测 0.34ms。

**四角锚点纯视觉、不响应拖拽**：时间线上没有"拖角缩放"这个操作（缩放是属性栏的事）。
尺寸压到 3px —— 太大就会被当成可拖的把手，那是骗人。

#### 蒙层的叠放顺序（这一条最容易错）

```
内容 → 离线灰蒙层(40%) → 锁定黑蒙层(30%) → 静音徽标 → 离线角标 → 锁角标
```

- 锁定蒙层**晚于**离线蒙层：早了会被那层 40% 灰冲淡，锁定看起来比离线还浅；
- 锁定蒙层**早于**所有徽标：晚了会把「离线」「静音」这些状态说明也压暗，
  用户就看不出"为什么不能动"了；
- 三个角标位置**必须错开**：静音在左上 y+4、离线在左上 y+18、锁在右上 ——
  三者可能同时成立（锁定 + 离线的静音片段）。

#### 主题兼容

高对比主题下"30% 黑蒙层"等于没画（黑底叠黑），所以 `[data-theme='contrast']` 里
换成 `rgba(255,255,255,0.14)` 白蒙层 + 更亮的锁定描边。这就是所有颜色走
`--v-tl-*` 变量的意义：只改值，不改一行绘制代码。

#### 光标（最便宜的可发现性）

| 悬停目标 | 光标 |
|---|---|
| 片段主体 | `grab` |
| 左右把手 | `ew-resize` |
| 锁定片段 | `not-allowed` |
| 标尺 | `pointer` |
| 空白轨道 | `default` |

### 3.25 2026-10-22 · S5 P0：裁剪吸附 / Ctrl 加选 / 多选删除 / 拖出界提示

按 `docs/s5-audit.md` 的 P0 清单落地。四项都是"接线 + 复用"，但**没有一项是纯接线**。

#### ① 裁剪吸附：复用 `snapFrame`，但要抽成函数

移动早就有吸附，裁剪没有 —— 而裁剪恰恰是"必须贴齐相邻片段"的操作。

实现上抽了一个 `resolveTrimSnapped(doc, clip, handle, deltaFrames, alt)`：
拿到裁剪结果后，取**被拖的那条边**（左手柄看 `startFrame`、右手柄看末尾）去吸附，
再按差值二次 `resolveTrim`。这样 `resolveTrim` 仍然只管"clamp 到素材边界"，
不需要知道吸附的存在（纯函数语义没被污染）。

**这里踩了一个自己挖的坑**：第一版只在 `pointerMove` 里吸附，`pointerUp` 用原始
`deltaFrames` 重算 —— 实测"预览吸到 120、松手落回 119"。因为松手时是**重新算一遍**，
而 `deltaFrames` 里没有吸附的修正量。所以必须让两个时机走同一个函数，
并把 `alt` 状态存进 `drag`（松手时 `altKey` 已经拿不到了）。

#### ② Ctrl 加选：接线，但加选后不进入拖动

`store.toggleSelection` 早就写好、单测也过，**UI 零调用点**（和 S4 的悬停态同一个病）。

`pointerDown` 加 `modifiers.additive`，命中后 `toggleSelection` 并 `return`。

**为什么加选后不进入拖动**：现在拖动只作用于主选片段（批量拖动是 P1+），
如果 Ctrl 点击后还能拖，用户会看到"只动了一个"——比不能拖更困惑。
所以加选是"只选不动"，想拖就松开 Ctrl 正常拖。

顺带补了**多选的可视化**：`drawClip` 的 `isSelected` 现在算
`主选 || extraSelectedClipIds.includes(...)`。否则 Ctrl 点了三段只看到一段有描边，
用户会以为加选没生效（而按 Delete 会删掉三段）。

Mac 用 `metaKey`：只判 `ctrlKey` 的话，Mac 用户按 Cmd 加选会变成单选。

#### ③ 多选删除：普通删除 + 波纹删除都支持整批

- `removeSelectedClip`：`getSelection()` 全部删，**一个撤销步**；
- `rippleDeleteSelectedClip`：按轨分组，每个幸存片段左移"**它前面所有被删片段的时长之和**"。

第二个公式值得说：不是"只移最后一个被删片段之后"，而是按每个幸存片段自己前面的
被删总时长来移。这样**被删片段之间的间隔会被保留**（间隔是用户故意留的，
不该被波纹吞掉），和 PR/剪映的语义一致。

#### ④ 拖出界提示：区分两种"拒绝"

旧实现拖出轨道区只是 `?? drag.fromTrackId` 静默回弹 —— 片段原地不动、**没有任何提示**，
用户会以为"软件卡了"。现在 `drag.invalidReason` 分两种：

| 场景 | 提示 |
|---|---|
| 拖到轨道区外（标尺上 / 所有轨道下方） | 拖到了轨道区域外，已放回原位 |
| 视频拖到音轨 | 视频片段不能放到音频轨 |

只在 `deltaFrames !== 0` 时提示 —— "点一下就报错"比不回弹更烦人。

**注意区分**：拖出**画布**是另一回事（`onPointerLeave` → `cancel()`，那是"取消拖动"，
不该提示）。测试一开始拖出画布测"出界提示"，结果测的是取消，白跑一次。

#### 验证

`tests/verify-s5-p0.mjs` 10 项，全部走真实鼠标/键盘事件：

- 裁剪吸附：右端从 120 往左拖 1 帧 → 吸附回 120（差 0 帧）
- Ctrl 加选：1 → 2 → 再点一次回 1
- 多选删除：选中 2 个 → 删后 0 个（原 2）→ **一次撤销全回来**
- 波纹删除：尾段 180 → 0（左移 180 = 两段被删时长之和）
- 拖出界：位置不变 + 提示"拖到了轨道区域外，已放回原位"
- 性能：单帧重绘 4.34ms（数量级未回退）

**测试自身的两个坑**（都记在注释里）：
1. 第一次测吸附时拖了 12 帧（60px），离目标 10 帧远 —— **本来就不该吸**，
   误判成"吸附没实现"。阈值是 8px ≈ 1.6 帧，必须拖到 1 帧内；
2. 拖出画布 ≠ 拖出轨道区（见上）。

**数字**：576 单测 / 35 脚本；E2E 54 个脚本全绿；构建 631.5KB；82 文件 0 处非法换算。

### 3.27 2026-10-22 · UI 重构 S1.2：三栏百分比布局 + 拖拽 + 折叠

S1.0 的钩子、S1.1 的顶栏都只是"不挡路"。这一轮才是真正把三栏从
`110px | 1fr | 110px` 换成 opencut-classic 的 `25% | 50% | 25%`。

#### 布局

```
--v-topbar-h: 48px
--v-left-w: 25%   --v-splitter-w: 4px   --v-right-w: 25%
.v-body { grid-template-columns: var(--v-left-w) var(--v-splitter-w) minmax(0,1fr) var(--v-splitter-w) var(--v-right-w) }
```

中间用 `minmax(0, 1fr)` 而不是 `1fr`：`1fr` 的最小尺寸是 `auto`，预览画布的
固有宽度会把中间列撑破（1440 窗口下实测能撑到 2000+ 并出横向滚动条）。

#### 拖拽为什么不 setState

`pointermove` 每秒 60+ 次，`setState` 会让整个 `App`（含时间线 canvas、预览、
素材栏）重渲染 —— 拖动会明显发涩。所以拖动中**直接改根节点的 CSS 变量**，
浏览器自己重排（这一层只有 5 个 grid 子项，成本可忽略），松手才写 localStorage。

监听挂在 `window` 上而不是分隔条自身：4px 的细线，指针一离开元素就收不到
`pointermove`，拖动会"卡住"（S3 的轨道高度拖拽踩过同一个坑）。

#### 折叠

面板 `display: none` + 列宽写 `0px`。不用 `width: 0`：内部 padding / min-content
会撑住宽度（实测折叠后还剩 21px），而且"宽度 0 但元素还在"会让 Tab 键聚焦到
看不见的按钮上。

按钮贴在分隔条**顶部**（`top: 8px`）且折叠态常显 —— 面板 0 宽之后，
用户唯一能点的就是这颗按钮。

#### 三个真实 bug（都是 E2E 抓出来的，肉眼完全看不出来）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 拖分隔条完全没反应，只有折叠生效 | 4px 的条上放 12px 宽的折叠按钮并**居中** → 整条都是按钮，拖拽起点永远落在按钮上 | 按钮移到 `top: 8px`，中间 100% 高度留给拖拽 |
| 2 | 折叠左栏后**预览宽度从 842 变成 4** | 面板 `display: none` 后脱离 grid 流，剩下 4 项**自动放置往前挤一格**：左分隔条占了第 1 列（25%）、预览落到第 2 列（4px 分隔条列）、右栏落到第 4 列（4px） | 5 个子项全部写死 `grid-column: 1..5` |
| 3 | **窄屏媒体查询是死代码** | 挂载时无条件 `applyPanelWidth` 写行内 `--v-left-w: 25%`，行内优先级高于 `:root` 里的媒体查询 → 820px 窗口下左栏仍是 205px，缩略图挤成一列 | 新增 `hasStoredPct()`：**只在用户拖过时**才写行内值，否则交给 CSS |

第 2 个特别阴：**折叠右栏时断言是通过的**（只是尾部少一项，前面列号不变，
预览正常变宽），只有折叠左栏才暴露。这类"一个方向对、另一个方向错"的
布局问题必须两个方向都测 —— 所以 `verify-layout` 里 ⑤ 和 ⑦ 是两条独立断言。

第 3 个的教训是**测试要测真实路径**：一开始 ⑫ 的写法是"清 localStorage +
手动 `removeProperty` 掉行内值 → 断言 16%"，那样等于替出问题的挂载代码擦屁股，
**带 bug 也是绿的**。改成"清 localStorage → 缩到 820px → **真的 `location.reload()`**"
之后，带 bug 时读到 25.2%、修好后 16.1%，这条断言才算真的有牙。

#### 一处刻意的偏离：媒体查询不用 `clamp()`

`--v-left-w: 25%` 在 820px 窗口下只有 205px，装不下素材缩略图（`--v-thumb-w` 是 132px
再加两列）。用媒体查询在 ≤1024px → 20%、≤820px → 16% 覆盖变量。
不用 `clamp()` 是因为它返回的是长度，写进 `grid-template-columns` 会和
拖拽写的百分比打架（拖到 40% 后被 `clamp` 悄悄改回 16%）。

#### 验证

新增 `tests/verify-layout.mjs`（16 项，全部读 `uiLayout()` 的**实际像素**而不是 CSS 变量）：

```
① 默认 25.1 / 49.7 / 25.1        ① 两条分隔条都在
② 拖左 +120px：354 → 474         ③ clamp 到 40%（实测 40.2%）
④ clamp 到 15%（实测 15.1%）      ⑤ 折叠左栏 212 → 0
⑤b 折叠后展开按钮仍在             ⑤c 折叠后预览 842 → 1054（+212，正好是左栏宽度）
⑥ 展开恢复 212（不是回到 25%）     ⑦ 折叠右栏 354 → 0，预览 842 → 1196
⑧ 右分隔条反向（354 → 474）       ⑨ 刷新后左右宽度都保持
⑩ 三栏不重叠  ⑩b 右栏贴右边界     ⑪ 单帧重绘 3.9ms
⑫ 820px 窄屏自动收窄到 16%
```

全量 E2E 55/55、单测 576/35 脚本、`npm run check` 0 处非法换算。

**数字**：构建 635.7KB（+3.4KB，`splitter.tsx` + CSS）。

### 3.29 2026-10-23 · UI 重构 S1.4：时间线高度 50%（15%–70% 可拖）

**目标**：时间线从固定 220px 改成"占工作区 50%"，与左右栏一样可拖、可记忆，
**只动布局层**，时间线渲染/素材/业务逻辑零改动。

```
.v-workspace {
  grid-template-rows: minmax(0,1fr) var(--v-splitter-h) var(--v-timeline-h);
}
--v-timeline-pct: 50;                       ← 唯一真相（无单位）
--v-timeline-h: calc((100vh - var(--v-topbar-h)) * var(--v-timeline-pct) / 100);
```

**关键决定：百分比只存在无单位变量里**

`--v-timeline-h` 有三类消费者：grid 行高、预览 16:9 的宽度计算、命令栏/toast 的
`bottom` 偏移。后两者要求它是**长度**。如果直接把它定义成 `50%`，
`calc(100vh - 48px - 36px - 50% - 24px)` 里的 50% 会按**宽度**解析（width 语境），
预览尺寸直接算错。所以拆成 `--v-timeline-pct`（50）+ `--v-timeline-h`（派生长度），
只在这里换算一次。

**分隔条复用**：`ui/splitter.tsx` 抽成三面板共用（`PANELS` 表：轴 / 变量名 / 存储键 /
方向 sign / min-max）。时间线是 y 轴、`sign = -1`（往上拖变大）、范围 15–70、无折叠按钮
（高度归零后没有任何替代入口）。热区仍是 4px，与左右栏一致；拖拽时 `body` 加
`v-splitter-dragging--y` 把光标切成 `row-resize`。

顺带删掉了 `TimelineView` 里那个**从未接过事件**的 `.v-timeline__splitter` 占位
（`aria-hidden` 的空 div，一直是死代码），改成 `.v-workspace` 的第 2 行真分隔条。
三行都显式写了 `grid-row`（S1.2 的同一课，别依赖自动放置）。

**踩到的坑（预防性）**

- `--v-timeline-h` 是 calc 后，`uiLayout().vars.timelineH` 读出来是
  `calc((100vh - 48px) * 50 / 100)` 而不是 `363px` —— 任何"读变量做数值断言"的测试
  都会踩空。测试一律读 `uiLayout().timeline.h` 的实际像素。
- 15% 时时间线只有 109px（工具栏 28 + 标尺 24 = 52，剩 57px 不够一条 60px 视频轨），
  轨道区靠 `.v-tl-scroll` 滚动，属于预期行为，不是裁切。

**验证**：`tests/verify-timeline-height.mjs` 16 项全绿，其中三条是核心：

```
① 默认 363 / 726 = 50.0%（基准是"视口 − 顶栏"，不是视口）
②b 分隔条顶 407 = 预览底 407（正好在边界，不是差 4px）
⑧ 清掉记忆后回到 50%，且根节点**没有**行内 --v-timeline-pct
```

- 预览的宽度 calc 去掉 `--v-ctrlbar-h`（不再占布局高度）→ 1440×900 下画面

**补了两个控件**：控制栏原本只有「播放 / 时间码 / 音量」，**没有**上一帧/下一帧

**测试踩到的坑（重要）**

- 用**有音轨**的素材时，`play()` 会选音频时钟；无头浏览器里 AudioContext 不推进，

- 顺带发现 `element.click()` **绕过命中测试**：控制栏叠在画面上，
  必须证明它没被 canvas 盖住 —— 改成 `Input.dispatchMouseEvent` 真实点击 +
  `elementFromPoint` 命中自身，这条断言才有意义。

| 校验 | `scripts/check-timebase.mjs`（静态扫描非法时基换算） |

### 关键约束（架构铁律，破坏必出 bug）

1. **时基唯一换算点**：所有帧↔时间/素材帧↔项目帧换算必须走 `src/core/timebase.ts`。
2. **借来的 `VideoFrame` 禁止 close**（归池所有）；`ensureFrame` 交付的是 clone（归调用方）。
3. **fpsMilli 是"毫帧率"**（30fps = 30000），单位陷阱极多（详见第 9 节）。
4. **解码器池纪元（epoch）**：seek 时递增，迟到的旧 epoch 帧必须 close。

### 7.2 ✅ 已解决：R-050 的 postMessage 命令通道（2026-10-21 交付）

协议：宿主发 `{ type, id?, ...参数 }`，编辑器回 `{ type, id?, ok, ...结果 }`，**一请求一响应**。
`id` 原样回传（宿主可并发发多条），响应回到 `event.source`（不写死 parent）。

| 命令 | 行为 |
|---|---|
| `getProject` | 回 `{ ok:true, project }`（完整工程 JSON，含素材元数据） |
| `setProject` | 归一化后 `replaceDoc`，回 `{ ok:true, schemaVersion }`；结构非法回 `E_INVALID_PROJECT` 且**当前工程不变** |
| `importAsset` | `buffer` / `dataUrl` / `url` 三选一；带 `assetId` = **R-054 重连**（字节绑回已有素材，不新建、不自动上轨） |
| `export` | `mp4`/`gif`/`wav`（`audio` 是 wav 旧别名），可带区间；回 `{ filename, mime, size, buffer }`，**buffer 用 transfer 送**；`webm` 明确回 `E_UNSUPPORTED_FORMAT` |

实现分三块：`host/commands.ts`（分发与回包）、`host/projectInput.ts`（工程归一化，纯函数、可在 Node 单测）、
`PostMessageAdapter`（协议与 transfer）。事件侧新增 `exportProgress`（按 5% 节流，避免逐帧刷屏）与 `exportDone`。

**交付时踩到两个真 bug**（都是"看着能用、实际静默失效"那类）：
1. **`?src=` 与命令通道互斥**：`pickAdapter()` 先判 `?src=` 就返回 `UrlParamAdapter`，
   于是"iframe + `?src=`"既没有命令通道、也发不出 `ready` —— 宿主永远等不到响应。
   修法：嵌入优先，`PostMessageAdapter` 自己接 `?src=` 当初始素材。
2. **T18 的断言把 bug 当契约**：`③ postMessage getProject → not_implemented` 断言的正是"没实现"，
   实现之后测试反而变红。已改为"回工程本体"（与 T19 推翻 webm 拒绝断言同一类处理）。

### 7.3 ✅ 已解决（保留结论，别重复排查）

#### R-057 多机位（切分 + 可见性切换）

- **不新建片段，只切分 + 开关 `enabled`**：多机位语义是"这一刻显示哪个机位"，不是"重排时间线"。
  切分保持素材入出点连续（不丢帧），每个区间只开一个机位；渲染层本来就跳过 `enabled === false`，
  **渲染代码零改动**。
- **一次 dispatch = 一个撤销步**：切分与开关在同一批操作里，撤销一次整批回滚。
- **"跟说话人"用音频能量近似**：`mixTimelineAudio` 单轨混音 → 取绝对值均值，哪条轨这一段更响就切谁。
  一人一麦的访谈好用；共享房间麦会退化成"谁离麦近切谁"——**这不是 bug，是没有说话人识别的必然结果**。
- **时间线比切换间隔短时必须报错**：只有一段时"多机位"退化成"挑一个机位全程用"，
  产出一堆关轨操作会让用户以为生效了。现在直接回可读错误（带实际时长与当前间隔）。
- **`enabled` 是硬指标**：两条都开=重影，两条都关=黑屏。E2E 逐帧扫 240 帧，每帧恰好 1 个机位可见。
- **入口可达性**：第二条机位轨靠"双击素材时播放头已被占用 → 自动落 V2"（见 §3.6）。
  没有那条落轨规则，多机位在界面上是触发不到的（功能做完了但用户用不上）。

#### R-056 蒙版（矩形/椭圆 + 羽化 + 关键帧）

- **能力边界**：**不做自动跟踪**。真正的跟踪要视觉模型逐帧找目标；这里提供"关键帧蒙版"——
  不同时间点摆好位置，中间帧线性插值（所有剪辑软件里"手动跟踪"的标准做法）。
- **坐标口径**：`x/y/w/h` 都是 0..1 相对值，与分辨率解耦——换分辨率（R-031）后蒙版不会跑偏。
- **羽化用 smoothstep**：高斯要采样半径内多个点，4K 全屏逐像素成本高一个数量级。
- **关键帧存在 effect 上**（`Effect.keyframes` 本来就字段），属性名 `mask.x/y/w/h`，
  由 `maskOf(clip, 相对帧)` 采样——不需要改 clip 的关键帧管线。
- **混合路径**：遮住的区域 `mix(bg, blended, alpha)` 露出背景，而不是变黑。
- **语义口径（别改反了）**：`maskAlphaAt` 是"**区域内保留、区域外遮住**"。所以
  "遮住左边" = 区域左半 + `invert:true`；"只露左边" = 区域左半 + `invert:false`。
  `invert` 在 params 里存 **1/0**（`maskOf` 判的是 `=== 1`，存 boolean 会被静默当成 false）。
- 入口两条：命令栏方位词（本地规则，不调模型）+ **属性栏「蒙版」组**（形状/左/上/宽/高/羽化/反向/移除）。
  细调参数时**必须保留 `current.keyframes`**，否则一拖滑块就把手动跟踪的关键帧抹了。
  命令执行后会 `setSelectedClipId` 选中目标片段——否则属性栏是"未选中"态，用户根本找不到参数。
- **验证**：E2E 分区域量（左半 126.4 → 5.6、右半 127.7 → 127.7），而不是只看全画面均值。

#### R-058 3D LUT（.cube → 3D 纹理）

- **为什么用 3D 纹理**：LUT 是"RGB→RGB 三维查表"，CPU 上每像素 8 次采样会卡死 4K；
  `sampler3D` + LINEAR 过滤是硬件干的活，一次采样搞定。
- **坐标要半像素偏移**：格点在 `(i+0.5)/N`，直接 `c*N` 采样会整体偏半格（颜色偏一点，很难发现）。
- **纹理用 RGBA8**：8bit 在 33³ 下误差 < 0.5/255；浮点纹理在部分设备不支持 LINEAR 过滤，
  会让 LUT 变"块状"——宁可少点精度也不要设备相关的不一致。
- **占位纹理必须绑**：`sampler3D` 不绑任何纹理时整个 draw 会失效，所以初始化时建一个 1×1×1
  的占位纹理常驻在 texture unit 3，`u_hasLut=0` 时走恒等分支。
- **`.cube` 原文存进 effect params**：工程文件自带 LUT，换机器也能用（代价是工程文件变大）。
- 边界：只支持 `LUT_3D_SIZE`（拒绝 1D LUT），**不做色彩空间转换**；2D 降级路径不支持 LUT。

#### R-059 字幕（SRT 导入导出 + 落到时间线 + 语音识别通道）

- **边界**：**客户端不做 ASR**（本地跑不动，云端要额外通道）。但**通道已经通了**：
  宿主实现 `AIModelPort.transcribe()` 就能"一句话生成字幕"，见下面"语音识别通道"。
- **容错**：坏块跳过、好块照用（缺序号、`.` 代替 `,`、时间轴后带坐标、多余空行都认）。
- **整段替换**：`buildSubtitleReplaceOps`（SRT 导入与语音识别共用）先删所有文本片段、
  再逐条新增，全在同一批操作里（一个撤销步）。字幕是**唯一**的——重复识别不该叠两份。
- **时间口径**：`msToFrame` / `frameToMs` 收进 timebase（SRT 是毫秒定义的格式），
  调用方不写裸除法——时基守卫会拦，而且迟早和别处不一致。
- 入口：顶栏「工程」菜单 → 导入字幕（SRT）/ 导出字幕（SRT）；
  命令栏「自动生成字幕 / 帮我转写」→ 走宿主 ASR 通道。

#### 语音识别通道（R-059 的最后一公里）

- **端口是可选方法**：`AIModelPort.transcribe?(request)`。不实现就是没这个能力，
  **绝不兜底成"返回空数组"**——那会让用户以为"识别完成了，只是没人说话"。
- **输入格式统一在客户端**：混音（48k 立体声）→ 下混单声道（取平均，不取最大）→
  重采样 16k 线性插值。宿主不该知道我们的工程采样率和声道数。
- **宿主输出不可信**：`segmentsToCues` 清洗时间戳倒着/乱序/重叠/空文本/负时间；
  一个坏片段会让整条字幕轨错位（后面的按错位置叠上去，用户只能全删）。
- **整段静音不调宿主**（`rms < 1e-4` 直接拒绝）：省一次网络往返，也给可读原因。
- **上限 30 分钟**：16k 单声道 30 分钟 ≈ 115MB，超了给可读拒绝而不是让浏览器 OOM。
- **测试怎么验的**：`verify-transcribe` 用 `__VEDITOR_TEST__.installTranscriber()` 装假宿主，
  它检查自己收到的音频（16000Hz / 128000 采样 / rms 0.088）——这段链路只有真 WebCodecs 能跑，
  单测证明不了。

#### R-033 转场（冻结帧溶解）

- **为什么用冻结帧而不是真素材溶解**：AI 生成的片段首尾就是内容边界，向外取帧会越界
  （`mapProjectFrameToAssetFrame` 抛错）。折中：窗口以接缝为中心，前半 A 正常播、B 冻在首帧，
  后半 A 冻在末帧、B 正常播——**时间线长度与两侧内容都不变**。
- **时长上限 = 片段一半**（`maxTransitionFrames`）：窗口是"接缝中心"的，超过一半就会越过片段边界，
  片段结束时进度还不到 1 → 画面永远半透明。三处共用这条规则：属性栏（拖不出来）、
  工程导入（宿主可能送旧数据）、渲染（兜底）。取一半而非"不超过片段"，是为了进出都有转场时
  中间仍留一整段完全不透明的画面。

#### R-055 曲线调色（4 点分段线性）

- **为什么不是样条**：样条要解方程、要处理过冲，而着色器每像素都算一遍；4 点分段线性
  （端点固定 0/0 与 1/1，中间两点可调）已能表达"提亮暗部 / 压高光 / 加对比"，且 JS 与 GLSL
  各 10 行、公式一致，不会漂。
- **顺序**：先调色（线性+混色）后曲线（任意映射）——用户调完滑块再用曲线收口。
- **2D 降级路径**用 256 项 LUT 逐像素映射（慢但正确，只在 WebGL2 不可用时走）。
- **自然语言**：`curveFromPhrase` 认"对比更强/更弱、更亮、更暗"；"对比更强"这类不含动词的说法
  会被 `classifyTone` 保守判成提问，命令栏为此加了一层"非疑问句即命令"的放宽。

#### R-061 音频降噪（噪声门 + 人声增强）

- **为什么不是谱减**：FFT + 噪声谱估计 + 音乐噪声处理是一整个 DSP 子系统；而口播最常见的
  问题是"底噪一直响"，噪声门 + 高通 + 存在感提升能解决 80% 的听感问题，且**逐样本可预测**。
- **无状态**：每次处理 0.5s 一块，不依赖上一块（预览是分块调度的，跨块状态在 seek 后会爆音）。
- **软门限**：阈值 ~ 阈值+6dB 线性过渡，避免硬切在临界点"抽气"。
- **预览与导出同一个函数**：`applyDenoise` 在 `audioEngine`（预览分块）与 `audioMix`（导出混音）
  各调一次，顺序都是"先降噪、后音量包络"。
- **自然语言入口**：`parseDenoiseRequest`（降噪/去噪/底噪/人声增强），在调模型之前拦下——
  这是本地 DSP，模型帮不上忙。
- 参数：门限 −70..−20dB、增强 0..100%，默认 −42dB / 50%。

#### R-063 触屏适配（平板 ≥768px 可完成全部 P0 操作）

- 窄屏只**收窄左右栏**（110 → 96 / 88px），**不缩时间线高度**：
  canvas 高 = 标尺 24 + 轨道数 × 56（3 轨 = 192），而轨道高是**命中测试的 JS 常量**，
  改 CSS 变量会让点击落到错误的轨道上（"两处同一规则"的经典坑）。
- 触屏最小可点 26px；属性栏标签降字号避免挤压控件。
- **不隐藏任何 P0 控件**：隐藏是最容易过测试、最坑用户的做法。
- 验证（820×1180）：无横向溢出、画布/播放/导入/导出都在视口内、加文本可用、**触摸拖动标尺能移动播放头**。

#### R-064 无障碍强化（读屏播报 + 高对比主题）

- `aria-live="polite"` 播报区：`播放头 00:00:02:00，sample-720p.mp4`。
  **必须节流 400ms**：播放时播放头每帧都变，逐帧写 aria-live 会让读屏连续朗读、完全听不清。
- 高对比主题：`data-theme="contrast"` + 一组颜色令牌覆盖（**只改颜色、不改尺寸**，
  否则用户切换后要重新找按钮）。选择存 `settings`，下次打开还记得。
- 画布也跟着换色：时间线/预览读的是 `getComputedStyle` 的 CSS 变量，属性选择器一处生效。

#### R-053 预设（把"一个片段的样式"存起来复用）

- **存什么**：变换（缩放/位置/不透明度/混合）、调色、音量与淡化、文字样式。
- **不存什么**：时间相关（起止帧/时长/速度）与转场 —— 套用会改变片段长度或与邻居的关系，
  那是"剪辑决定"，不能靠一个按钮替用户做；文字**内容**也不存（预设是样式，不是复制）。
- **只存被改过的字段**：把默认值也存进去，套用会把目标片段"重置"成默认。
- **一次撤销步**：每个字段一条 `setClipProps`（带 `from`），调色一条 `setClipEffect`，
  文字一条 `setClipText`，合成一批 dispatch。
- **存哪**：`settings` 的 `presets` 键（用户偏好，不是工程内容，换工程也还在）；上限 40 条，
  读取时逐条 `normalizePreset`（坏数据丢弃、越界值夹住），一条坏记录不会带崩整个列表。

#### R-054 工程文件迁出（一个文件搬走整份工程）

- **产物**：单个 `.vedproj`（JSON，缩进 2 空格，能 diff 能人读），带 `format/version/schemaVersion`
  信封 + 完整工程 + 素材清单。**不含素材字节**（4K 工程带素材是几个 GB，且 PRD 要求"素材待重连"）。
- **读回**：信封校验 → 版本校验 → **复用 `normalizeProjectInput`** 补字段（与宿主 `setProject` 同一条闸门）
  → 素材统一标 `offline`。失败一律给可读原因（"不是工程文件"/"版本过新"/"结构不合法"）。
- **换工程必须先 `resetPreviewSources()`**：旧素材源还挂在引擎里，不清会让新工程"借用"旧字节
  （看起来能播，其实播的是上一个工程的内容）。
- **重连**：素材卡「重新链接」在无句柄时改为选文件 → `importAssetFile(file, assetId)` 按 id 绑回
  （同一条导入实现，不新建素材、不自动上轨）。

#### R-052 代理媒体（4K 预览不再卡）

- **触发**：像素数 ≥ 4K 的 80%（`PROXY_MIN_PIXELS`）才转，1080p/1440p 零开销。
- **产物**：960px 长边（按**长边**压，竖拍不会变成 960×1706）的 MP4，**视频 + AAC 音频轨都要有**——
  否则切源后预览没声音（`decodeAudioRange` 读的就是注册时那份 probe 的音频样本表）。
- **存哪**：IDB `proxies`（DB 版本 1→2，升级时补建缺失 store）；刷新/重开工程直接复用，不重转。
- **两条路径分开**：`getPreviewSource`（代理优先）/ `getExportSource`（永远原片）。
  导出、粗剪分析都用原片——代理是降分辨率的，进成片就是画质事故。
- **切源必须 `unregisterAsset` 再 `registerAsset`**：只 register 会留着**旧源的帧缓存**，
  切过去取第 0 帧命中旧缓存 → 黑屏且永不自愈。这是本次踩得最久的一个坑。
- 实测：4K 每帧渲染 **42.2ms → 4.4ms**（软件渲染，约 9.6 倍）；代理 2.0s/60 帧，约 15 秒转完。

#### R-060 智能粗剪（一句话去掉长停顿）

- **分工**：模型只判"要不要剪、多长算长"；**位置由本地音频能量分析算**。
  模型看不到波形，让它给帧号一定是编的——这也是命令栏在**调用模型之前**就用规则拦下这条指令的原因。
- **分析**：整条时间线混音成 48k 立体声 → 20ms 窗口 RMS → dBFS 阈值（默认 −40）→ 合并成区间 →
  两端各收 0.1 秒余量（避免削掉字头）→ 短于阈值（默认 1 秒）的丢弃。
- **落地**：新增 `core/rippleDelete.ts`——**切两刀 → 删中间 → 整条轨后面左移**。
  没用 `compileRemoveRange`：那个函数剪尾只改出点，会在原地留洞；粗剪要的是"内容接上来"。
  多段区间**从后往前**处理，否则前一次的左移会让后面区间的帧号失效。
- **一次撤销步**：所有区间合成一批 ops 一次性 dispatch。
- **拒绝执行的两种情况**：没有音频信号；静音占比 > 90%（多半是无声素材，剪下去会把内容全删）。
- **上限 5 分钟**：要攒整段 PCM（5 分钟约 115MB）。

#### R-062 透明通道导出（RGBA PNG 序列 + ZIP）

- **合成器要开 alpha**：`createCompositor({ alpha: true })` 才会 `clearColor(..., 0)`，
  否则每帧都是不透明黑——文件扩展名对、内容全错，且不报错。
  预览与 MP4/GIF **必须保持不透明**（编码器不保留 alpha，会变暗）。
- **ZIP 自己写**（`src/export/zip.ts`，store 模式 + CRC32）：PNG 已经压过，再 deflate 没收益，
  不值得为它引入压缩库。文件名置 UTF-8 标志位（bit 11），中文工程名不乱码。
- **上限 600 帧 / 4 亿像素**：序列是"攒齐再打包"，不设闸的话长视频会导出到 90% 才把标签页打爆。
- 产物：`frame_000001.png` 起连续编号 + `frames.json`（fps / 起止帧 / 尺寸 / 编号规则）。

#### `<veditor-panel>` 在矮容器里溢出

**现象**：宿主给 `600px` 高的容器时，panel 内部 `.v-app` 计算高度 **1233px**，
播放按钮被挤到 `y=841`（视口 800）→ 用户点不到。

**真正的根因**：`main.css` 是通过 **document 的 `<link>`** 加载的，而 shadow DOM 是**样式隔离**的。
panel 内的 `.v-app` 等元素**完全没拿到 CSS**（`appDisplay: "block"`、`appHeight: "1233.58px"`、
`appPosition: "static"`）—— 不是 `height: 100%` 失效，是**整条 CSS 都没进 shadow DOM**。

**修法**：`connectedCallback` 里克隆 document 的 `link[rel="stylesheet"]` 到 shadowRoot。
修后 `appHeight: 600px`、`appDisplay: flex`、`appPosition: relative` 全部正确，
播放按钮在视口内、点击后 `aria-pressed: true`（真的播放）。

**之前试过、都无效的三个方案**（方向错了，根因是"样式没进 shadow"，不是"高度链断裂"）：
1. `container-type: size` + `100cqh`（容器查询循环）
2. ResizeObserver 写 CSS 变量
3. mountPoint `position:absolute; inset:0`

**教训**：CSS 样式没生效时，先用 `getComputedStyle().display` 判断"是不是整条样式都没了"，
再决定是调高度链还是调样式注入。

#### 播放中卸载 `<veditor-panel>`，rAF 循环是否被停

**答案：会停。** 用 CDP `Input.dispatchMouseEvent` 真实点击 shadow DOM 里的播放按钮
（脚本 `.click()` 不翻转 React 状态），播放启动 rAF 循环；卸载后 rAF 立刻归零。
20 次挂载/卸载循环无累积（每轮挂载后 rAF=1~2、卸载后 0）。

`tests/verify-panel-leak.mjs` 已覆盖：① 挂载成功并出画布 ② 卸载后 rAF 回基线 ③ setInterval 回基线
④ AudioContext 全关 ⑤ 20 次后三者均无累积。

### 7.4 ⚠️ 设计取舍（非 bug）

#### VFR 素材的内容节奏不精确

`mapProjectFrameToAssetFrame` 是**线性帧号映射**（假设 CFR）。VFR 素材被当作
"平均帧率的 CFR"处理：**总时长正确**（4.0s 的素材导出 4.00s），但内容节奏有偏差
（前段拉伸、后段压缩）。要精确需按 PTS 映射（改 timebase 契约）。

#### 编辑器是"模块级单例"，同页只能一个实例

`store` / `ensurePreviewEngine()` 的引擎与解码器池 / `previewSource` 的模块级 `engine`
——每个模块只有一份。同一页面**不能同时**跑主 App 和 `<veditor-panel>`（后者预览永远黑屏）。
宿主集成时用 `?bare=1`（只注册 custom element、不挂主 App）。

#### GIF 帧率精度

GIF 的 15fps 受 GIF 延迟精度（10ms 单位）限制，实际约 14.3fps。

## 9. 关键踩坑记录（**避开这些，别重复劳动**）

### 9.1 单位陷阱（最容易出 bug）

- **fpsMilli 是毫帧率**：30fps = **30000**，不是 30。
  `1e9 / defaultDurationNs` 得到的是帧/秒（30），要 ×1000 才是毫帧率（30000）。
  这个坑让 webm 帧率算错 1000 倍、整个时基崩塌（T19）。
  同类坑：`speedOf` 返回 1000 而非因子 1（C3）。
- **`allocationSize()` 默认按 RGBA 计**：1920×1080 算 7.9MB（实际 I420 只 3.1MB），
  虚高 2.67 倍会让帧缓存预算瞬间吃满 → LRU 立刻淘汰刚存入的帧 → 交付已 close 的帧 → 黑屏。
  **必须显式 `allocationSize({ format: 'I420' })`。**

### 9.2 WebCodecs 的坑

- **`VideoFrame.clone()` 必须在 `storeFrame` 之前**：入缓存会触发 LRU 淘汰并 close 原帧。
  交付原帧给调用方 = 交付一个"已关闭帧"（`displayWidth === 0`）。
- **VP8/VP9 的 `VideoDecoderConfig.description` 必须是 `null`**：传了 CodecPrivate 会让
  configure 静默失败 → 永远黑屏（description 只对 AVC/HEVC 有意义）。
- **WebCodecs 不解旋转**：手机竖拍的旋转必须自己从 mp4 `tkhd` 矩阵解析（`atan2(b, a)`），
  渲染时 CPU 旋转。`displayWidth/Height` 是**存储尺寸**，不是显示尺寸。
- **Chromium "持有帧红线"**：池持有 ~9 帧解码器就停摆，缓存配额受此约束。

### 9.3 测试的坑

- **测「挂载 / 初始化」逻辑时，别在测试里手动补齐被测代码的副作用**：S1.2 的窄屏 bug 在挂载
  `useEffect` 里（无条件写行内 `--v-left-w: 25%`，把媒体查询盖成死代码）。第一版断言写的是
  "清 localStorage + 手动 `removeProperty` 掉行内值 → 断言 16%"，**带 bug 也是绿的**。
  改成"清记忆 → 改窗口 → 真的 `location.reload()` → 断言"才有牙（带 bug 读 25.2%、修好 16.1%）。
  **判据**：测试里出现"手动补齐被测代码本应产生的结果"，这条断言就没牙。
- **布局类改动要两个方向都测**：S1.2 折叠**左**栏时预览宽度变 4px（面板 `display:none` 脱离 grid 流，
  剩下子项自动放置往前挤一格），但折叠**右**栏时断言完全通过（尾部少一项、前面列号不变）。
  凡是"从某一侧移除元素"的布局，只测一侧等于没测。
- **ffmpeg 的 `volumedetect` / `signalstats` 输出到 stderr**：`execFileSync` 只返回 stdout，
  会误判"静音/黑屏"。**必须用 `spawnSync` 取 `run.stderr`。**
- **React 17+ 的 `onBlur` 监听的是 `focusout`，不是 `blur`**：派发 `blur` 事件不触发提交。
- **素材卡片 `textContent` 不含文件名**（只有"内存"状态标签）：按名字找卡片必然失败，
  用 `assets()` 索引与卡片顺序对应。
- **默认 zoom 下多片段工程只显示开头约 22 帧**：坐标点击选不到后面的片段，
  用 `selectClip(clipId)` 测试钩子。
- **`fixture` 目录有同名不同内容的素材**（`hardline/` 与 `compat/` 的 webm）：
  fixture server 的查找顺序要 **compat 优先**。
- **`void renderPreviewFrame(...)` 会吞掉所有异常**：黑屏时没有任何提示。
  必须 try/catch 并记录 `lastRenderError`。
- **测试覆盖了 A 路径 ≠ B 路径对**：T18 只测 `?src=`，却宣称"custom element 支持"，
  实际 `src` 属性根本没实现。
- **断言"对称指标"等于没断言**：蒙版只量全画面均值时，"遮左"和"遮右"结果一模一样，
  于是方向反了的 bug 一路绿灯。**凡是左右/正负/增减对称的效果，必须分开量**
  （`previewSnapshot(region)` 就是为此加的）。
- **受控 input 里 setState 是异步的**：`input` 事件后紧接着 `click` 按钮，可能点在一个
  还是 `disabled` 的按钮上——浏览器直接吞掉，表现为"什么都没发生 + 15 秒超时"。
  先 `waitFor(按钮可点)` 再点。
- **不要在测试里写死 IndexedDB 版本号**：应用加 store 时会升版本，写死旧版本抛 `VersionError`。
  用 `indexedDB.open(name)`（不传版本）。
- **沙箱对单轮批量删除有闸**（约 50 次 `rmSync`）：连续跑几十个 E2E 时，靠后的脚本可能在
  "清理临时目录"这一步失败，看着像功能坏了。单独跑一次即可确认。
- **固定 `sleep(N)` 是全量跑的头号 flake 源**：单跑够、连跑不够（机器被前面几十个脚本压着）。
  一律改成"轮询条件直到成立（带超时）"——真 bug 仍然会失败，只是等得更久。
- **`decodeTest()` 会 bump epoch、取消正在跑的渲染**：诊断代码要排在拍快照**之后**，
  否则快照/统计拿到的是被取消的那一帧（层数 0 / 全黑），看起来像"渲染坏了"。
- **诊断指标也会误报**：`decodeFailures` 曾把"seek 被新 epoch 取消"算成失败，
  于是负载下永远非 0，测试要么假红要么被迫放宽断言。**指标要区分"失败"和"被取代"**。
- **统一 catch 会掩盖真 bug**：`store.record` 里为了把"锁定拒绝"转成错误条而 catch 全部异常，
  立刻让 `clip-ops` 的"非法倍速应当抛"用例变红。**只捕获你明确知道怎么处理的那一类错误**
  （这里用 `TrackLockedError` 区分），其余照旧抛——否则非法参数会变成一条不起眼的错误条。
- **自己起的服务别占测试端口段**（5180–5223）：`serve-media.mjs` 一开始用了 5180，
  正好撞上 `verify-c-ui`，它起 dev server 时端口被占 → 报"dev server 未就绪"的**假红**。
  开发工具默认端口要放在测试段之外（现在用 5300）。
- **"逐块处理"要小心需要上下文的算法**：sinc 重采样/滤波这类核需要块边界外的样本，
  逐块调用会让每块边缘失真。**要么整段处理，要么给足 overlap**。
- **测试素材的"参数多样性"也是覆盖度**：采样率/声道数/帧率这些维度只要恰好都一致，
  相关 bug 就永远测不出来（逐块重采样 bug 藏了很久，因为素材几乎全是 48k）。
- **别把状态重置写在 effect 里**（"打开即重置"）：effect 在首帧后才跑，会和用户的第一下输入抢时序。
  用条件挂载让初始 state 天然干净。
- **E2E 的前置条件太顺 = 替用户作弊**：交互类 E2E 全都先 `selectClip()` 再拖，
  正好绕过了"手柄要求先选中"这个真问题，于是用户实测时"裁剪坏了"。
  **能用真实指针事件走的路，就不要用测试钩子抄近路。**
- **误导性报错比没报错更糟**：拖缩略图触发"请转为 mp4"，用户会以为视频格式不支持，
  实际拖进去的是那张 PNG。**报错前先确认"用户到底拖了什么"。**
- **E2E 绕过的入口 = 用户走不通的入口**：R-057 的 E2E 曾用 `setProject` 硬造双轨工程，
  于是"界面上根本放不了第二段素材"这件事一直没被发现。**能走 UI 就必须走 UI**。
- **E2E 跑的是 `dist/`，不是你刚改的 `src/`**：2026-10-22 那一轮全量跑出 5 处红
  （`verify-interaction` ⑦⑩⑪、`verify-panel-leak` ①、`verify-multiclip` 超时），
  排查半小时才发现 `dist/build-id.txt` 是 03:42、右键菜单修复是 03:56 落的 ——
  改完源码没 `npm run build` 就跑 E2E，测的是上一版。单跑全绿。
  **规矩：改源码 → `npm run build` → 再跑 E2E**；看到一片红先看 `build-id.txt` 对不对。
- **`RUN_FIRST` 的过滤顺序不等于数组顺序**：`filtered.filter((n) => RUN_FIRST.includes(n))`
  保留的是**字典序**，于是 `verify-proxy` 排在 `verify-realworld` 前面 —— 恰好是注释里说会假红的
  顺序（4K 代理转码先跑、4K 预览后跑 → `decodeFailures=1`，单跑 0）。要按书写顺序就必须显式
  `sort((a,b) => RUN_FIRST.indexOf(a) - RUN_FIRST.indexOf(b))`。
- **坐标类 E2E 的几何必须在点击前**重量**，而且要等它稳定**：时间线会"跟着播放头滚"
  （`ensurePlayheadVisible`），内存模式警告条出现/消失还会把整条时间线推上推下。
  "读 scrollX → 算坐标 → 点击"之间只要动过一次，点就落偏 ——
  表现为"点空白处播放头不动"（实际点到了轨道头）或"右键弹出空白菜单"，
  而且**只在某些轮次复现**。`verify-interaction` 现在用 `stableScroll()`：
  轮询到 scrollX 连续两次不变，再顺手重量 `left/top/zoom`，并把 `scale` 从常量改成函数。
- **性能断言在共享机器上只是趋势，不是不变量**：`verify-proxy` 的"代理更快"
  曾因 5.2ms vs 5.7ms 被判红（单跑是 6.4 vs 9.8）。改成"快 20% 以上算明确更快；
  差 15% 以内算噪声（**结果里写明**）；代理反而慢 15% 以上才红"。
- **`await` 之后就不再是"用户手势"**：`requestPermission` / `input.click()` 这类要求
  transient activation 的 API，只要前面 `await` 过一次（哪怕只是读 IDB），
  在某些环境（内嵌面板/受限 iframe）就会被静默拦掉。**要弹选择器就第一件事弹**，
  把需要授权的动作拆成独立按钮。
- **"只改状态不改源"等于没改**：`restoreSession` 把 `asset.status` 标成 `ok`，
  但预览源是内存态、刷新后是空的 —— 状态对、画面黑。**任何"恢复"流程都要问：
  消费方（解码器/引擎）那边真的拿到字节了吗？**
- **同步接口内部异步会制造竞态**：`unregisterAsset` 里 `void pool.unregister(...)`，
  和紧跟着的同步 `register` 打架，把刚注册的源删了（表现：重链成功但永远黑屏）。
  要么把清理放进 `register`（覆盖语义），要么提供同步的 `invalidate`。
- **`release` ≠ `unregister`**：前者只关会话、保留源，下一次取帧会重新建会话并成功解码。
  想"让这个素材不可用"必须连源一起删。
- **`preserveDrawingBuffer: false` 的 WebGL canvas 在"不重绘"时内容未定义**：浏览器合成过一次
  之后就不再保证缓冲有效。"有变化才重绘"的预览一旦暂停，任何一次重新合成（缩放窗口、切主题、
  切标签页回来）都会显示出未定义内存——**黑白噪点、横条纹**。要么保留绘制缓冲，
  要么常驻 rAF 每帧重画（费电）。**任何"按需重绘"的 WebGL 画布都要考虑这一点**。
- **"空内容"必须有自己的成功语义**：拿 `exact` 判断"画好了没有"时，空内容在 element 模式下
  恒为 false → 重试预算被耗在"重画一张本来就该全黑的画面"上 → 预算满后**再也不重绘**。
  给空帧一个显式标记（`empty`），比让上层去猜"没层是不是失败"可靠得多。
- **`AudioParam.value` 在 `setTargetAtTime` 自动化期间读不到实时值**：实测一直是初始值。
  于是"静音有没有真的到音频链路"在 E2E 里完全测不出来——这类 bug 会反复回归。
  要么直接赋值，要么额外维护一份目标值供断言。
- **提前排期的音频不受文档状态影响**：预览的 PCM 是提前 1–3 秒排好的，改 `muted` 对已排期的块
  毫无作用。要"立刻静音"必须有**实时可改的增益节点**（轨道闸门），不能只改数据。
- **画布上的压暗必须画在"最后一层底色"之后**：轨道头列会再铺一层 `rulerBg`，
  先画的蒙层会被整块盖住——表现为"代码明明加了，画面一点没变"。
- **滑块"只改显示、松手才提交"是个陷阱**：`onChange` 只写本地 state、`onPointerUp` 才写 doc，
  一旦 `pointerup` 落在别处（点轨道跳值 / 键盘调 / 触摸在别处抬起），界面和实际值就永久分叉。
  症状有两种：显示 5% 实际 100%（"调小了还是响"）和显示 5% 实际 0（"这条轨没声音"）。
  **要么 onChange 就提交（用 `mergeKey` 合并撤销步），要么在界面上明确标出"未提交"**。
- **`setTargetAtTime` 在 suspended 的 AudioContext 上不推进**：`ctx.currentTime` 不动，
  斜坡永远到不了目标值。用户"播放前先调音量"会完全无效。要么直接赋值，要么在 `resume()` 后补一次。
- **`overflow: visible` 的画布会吃掉下面的一切**：时间线画布高 = 标尺 + 轨数×56，
  区域高度固定时，多出来的轨道会被裁到视口外——"看得见但点不到"和"根本看不见"两种表现。
  有动态高度的内容必须给它滚动容器。
- **给 `EphemeralState` 加字段时，painter 要用 `?? null` 兜底**：测试里常手搓一个
  "只填了用得上的字段"的对象（`verify-t15` 的 `emptyEphemeral()`），新字段那边不会自动补。
  `undefined !== null` 成立 → 走进不该走的分支 → 整条时间线画不出来（实测 t15 红了 107 秒，
  日志只有一句"页面未完成"，极难定位）。painter 是纯渲染函数，不该因入参少字段就崩。
- **写在模板字符串里的测试脚本不能出现反引号**：`verify-t15` 把浏览器脚本塞在
  `const PAGE = \`…\`` 里，我在那段注释里用了 markdown 反引号（`` `dropGhost` ``），
  直接把模板截断 → `SyntaxError: Unexpected identifier`。同理 `${` 也要小心。
- **"点了没反应"必须用真实文件/真实产物验证**：菜单项只断言"点击不报错"等于没断言，
  要用 `Browser.setDownloadBehavior` 把产物落到目录，再校验文件头
  （WAV 要 `RIFF....WAVE` 且字节数 > 44）。`verify-audio-menu.mjs` 就是这么钉的。
- **有音轨的素材在无头里播放头不动**：`play()` 会优先选音频时钟，而 AudioContext 在
  无头浏览器里不推进 → `derivedFrame()` 永远算回 anchor 帧。表现是
  `aria-pressed=true` 但 `playheadFrame()` 从 2 到 2（看起来像"播放键坏了"）。
  要测"播放真的推进"必须用**无音轨素材**（`silent-720p.mp4` 实测 2 → 62）。
- **`element.click()` 绕过命中测试**：它不关心元素是否被别的元素盖住。
  凡是被移动/叠加过的控件（S1.5 的控制栏浮在 canvas 上），必须用
  `Input.dispatchMouseEvent` 真实点击 + `document.elementFromPoint` 命中自身，
  否则"点不到"这类回归永远测不出来。

### 9.4 架构级陷阱

- **"旋转"必须乘在缩放之后**：`u_rotate * (a_pos - 0.5)` 然后 `* u_size` —— 单位正方形
  转 90° 还是那个正方形，几何上是**恒等变换**，于是画面完全没转、只有宽高互换生效了。
  正确顺序：先 `(a_pos-0.5) * u_size` 进像素空间，再 `u_rotate *`，再 `u_flip *`。
  这个 bug 肉眼看不出（片段变宽了、属性栏也显示 90°），只有量"左右是否留黑"才抓得到。
- **"旋转后的尺寸"不能用"包围盒互换"算**：16:9 转 90° 应该是 9:16 贴满高度（左右留黑），
  用 `swap(fit)` 会把它拉伸回 16:9 填满画布，人脸横向拉长 1.78 倍。
  必须按**旋转后的画幅**重新 contain：`fitSize(源高, 源宽, 画布宽, 画布高)`。
- **`createClip` 只在参数里带了才写可选字段** → 序列化必须逐个显式归一化。
  `normalizeClip` 漏了 `role` 就等于"存盘再打开，分离音频的片段又同时出画出声"（音量翻倍）。
  加任何 `Clip.xxx?` 可选字段时，**同步改 `normalizeClip`**，否则只有存盘才发现。
- **窄容器里的 `1fr 1fr` 会溢出被裁**：右属性栏 110px，两列各 53px 撑不住 min-content，
  按钮溢出后 `elementFromPoint` 命中容器本身 —— 表现是"按钮看得见、点不到"。
  窄栏一律单列（`grid-template-columns: minmax(0, 1fr)`）。
- **ephemeral 状态改了 UI 不一定刷新**：`notify()` 后 `useDerived` 在 doc 未变时返回
  **同一个引用**，React 判定快照没变就不重渲染（按钮标签停在旧值）。
  读 ephemeral 的组件要 `useVersion()` 订阅"任何变化"。

- **两处重复的 clamp 规则会互相打架**：`playbackClock.maxFrame` 与 `store.syncPlayhead`
  都用 `duration-1`，导致片尾追加片段时重叠 1 帧。**同一条规则只能有一个定义点。**
- **`exact = layers.length === 0 || missing === 0` 是错的**：全部层失败时 layers=0，
  反而被判"精确"，上层据此认为"画好了"不再重试 → 黑屏永久停留。
  正确语义：`missing === 0 && (!hasVisible || layers.length > 0)`。
- **并发 renderFrame 共享池缓存会互相淘汰**：必须串行化 + 合并中间请求。
- **`destroy()` 只卸载 React root**：transport 的 rAF、AudioContext 都在 useEffect cleanup 里，
  模块级单例（引擎/池）不随组件销毁。
- **`hidden` 属性会被自己的 `display` 盖掉**：`[hidden]` 的浏览器默认样式是
  `display: none`，但类选择器 `.v-tabpane__slot { display: flex }` 优先级更高 ——
  "隐藏"的元素照样占位、照样能点到。凡是用 `hidden` 藏 flex/grid 容器，
  **必须显式补 `[hidden] { display: none }`**。
- **"算在里面"还是"加在外面"必须用像素断言**：S1.3 的 44px 图标条如果写成
  "25% + 44px"，1440 下只多占 3%，肉眼完全看不出，但中间预览区被永久挤压。
  正确断言是 `内容区宽 = 左栏宽 − 44`（差值 0），不是"图标条宽 44"。
- **百分比只能存在"无单位变量"里，长度派生一次**：`--v-timeline-pct: 50` +
  `--v-timeline-h: calc((100vh - var(--v-topbar-h)) * var(--v-timeline-pct) / 100)`。
  若把 `--v-timeline-h` 直接定义成 `50%`，它在 `width: calc(100vh - … - 50%)` 里会按
  **宽度**解析（属性语境决定百分比基准），预览尺寸静默算错 —— 不报错、不崩，只是"看起来有点小"。
- **`calc()` 之后别用 `getPropertyValue` 做数值断言**：自定义属性的计算值是
  `calc((100vh - 48px) * 50 / 100)` 这串 token，不是 `363px`。测试要读元素实际 rect。
- **规格的每个数学公式都要有反例用例**：证明它不能被等价替换（时基 13.5% 相位错的教训）。
- **生死线断言必须有独立验证路径**（不共享代码）：如用 BigInt 独立实现 spec 公式做对拍。

## 12. 冷启动怎么接手（给新窗口 / 其他 agent）

1. 读 §1–§2（约 5 分钟）：知道是什么、做到哪、缺什么。
2. 读 §7.1（约 1 分钟）：**先知道哪些"只做了一半"**（4 条部分交付：蒙版无自动跟踪、多机位无说话人识别、LUT 无色域转换、字幕无语音识别），别把设计边界当 bug 去修。
3. 动代码前必读三个文件：`src/core/timebase.ts`（唯一换算点）、`src/core/types.ts`（数据结构）、
   `src/core/store.ts`（撤销栈 + 通知）。
4. 先跑基线：`npm test && npm run check`（约 15 秒，应全绿）。
5. 改完按 §6 的表找到对应 E2E 跑一遍，再 `npm run build` 看体积有没有异常增长。
6. 重要交付后更新四处：**§2 数字（连命令一起）**、§3 全史、§7 未交付项、§9 踩坑。
7. **测试脚本数量变了要一起改**：§2 的 E2E/单测行、§6 的两张表（单测表要能求和）、
   `package.json` 的 `e2e:*` 别名、`scripts/e2e-all.mjs` 是自动发现的（不用改）。
   单测表可用一行 python 校验：把所有 `| \`name\` | ... | N |` 的 N 求和是否等于合计。

> 一条经验：本项目 90% 的隐蔽 bug 都出在"**两处写了同一条规则**"或"**单位/返回值语义**"上
> （见 §9.4 与 §9.1）。改这类代码时，先搜全仓库有没有第二份实现。
