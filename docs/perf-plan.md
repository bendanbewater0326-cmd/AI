## 1. 实测结果（帧间隔 p95 / max，ms）

| 规模 | 静止 | 滚动 | 缩放 | 拖拽 | 音量滑块 |
|---|---|---|---|---|---|
| 0 段 | 5.1 / 9.9 | 5.1 / 5.4 | 5.0 / 10.0 | — | — |
| 150 段 | 5.1 / 5.2 | 5.1 / 5.2 | 5.1 / 10.0 | 5.1 / 5.2 | — |
| 500 段 | 5.1 / 5.2 | 5.1 / 6.6 | 5.0 / 10.0 | 5.1 / 5.2 | — |
| 2000 段 | 5.1 / 5.1 | **5.1** / 5.9 | **5.1** / 14.9 | **5.0** / **110** | **5.1** / **95** |

**结论**：所有规模下 p95 都顶满无头帧率上限——**没有任何持续性掉帧**。
2000 段（单轨极端规模）出现**偶发单帧尖峰**：拖拽 max 110ms、滑块 max 95ms（p95 仍 5.1ms）。

## 2. 对三条优化方向的逐项判定（如实反馈）

### 2.1 视口外片段懒渲染 —— **已经存在，无需开发**

`timelinePainter.drawClip` 首行就是视口裁剪（`box.x + box.width < 0 || box.x > viewport.width` 即返回）——
视口外片段只花一次 O(1) 坐标计算就被跳过，不进入任何绘制调用。这正是实测 2000 段滚动
依然 5.1ms 的原因：每帧遍历 O(n) 是纯算术（2000 次 clipBox ≈ 0.1ms 级），绘制量只与
视口内片段数（<50）相关。**重复建设无收益**。

### 2.2 属性栏参数调节防抖 —— **有实测依据，但仅极端规模可感**

音量滑块是 change 即提交（每个 0.05 步长一次 dispatch：apply ops → 新 doc → React 通知 →
时间线重绘）。500 段内无感；2000 段时连发 20 次出现 95ms 尖峰——瓶颈不在绘制，
在 **dispatch 全链路**（doc 深拷贝 + 订阅者通知）。

可做的**小优化**（低成本、有数据支撑）：滑块拖动中的提交改 **rAF 合帧**——
拖动期间每个 rAF 至多 dispatch 一次（最后一次值生效），松手语义不变。
影响面：`InspectorPanel` 音量 onChange 一处（淡入淡出已是失焦提交、无需改）。

### 2.3 素材缓存池预加载策略 —— **另一维度，本次未测**

预加载影响的是"播放起播延迟/拖动中解码跟帧"（音频调度已有 3s 预读 + 欠载统计），
不是时间轴帧率。现有调度器的 underruns 统计在全部 E2E 里都是 0。**没有实测问题支撑改造**；
若未来出现"长工程播放断续"，先读 `audioStats.underruns` 再决定。

## 3. 建议

| 项 | 判定 | 理由 |
|---|---|---|
| 视口外懒渲染 | **不做**（已存在） | drawClip 裁剪 + 实测 2000 段滚动 5.1ms |
| 滑块 rAF 合帧 | **做**（一个小改动） | 2000 段实测 95ms 尖峰有数据支撑；一处改动 + 一个 E2E 断言 |
| 缓存池预加载 | **不做**（无问题支撑） | underruns 全绿；等真实症状再说 |
| 大规模专项 | **不立项** | 500 段内（远超普通用户工程）无可测问题 |
